## Зачем

Контентные команды тратят время не только на создание материалов, но и на поиск тем, проверку сигналов, упаковку и публикацию. С ростом числа ниш, каналов и форматов эта рутина перестаёт масштабироваться.

Postify строится как контентная операционная система: она превращает поток материалов из выбранных источников в контентные пакеты и публикации, за качество которых можно отвечать — с историей решений, защитой от повторов и измеримой себестоимостью.

Платформа не привязана к одной тематике. Пользователь сможет собрать собственный контентный контур для любой ниши: дизайн, бизнес, крипто, образование, локальные новости или собственная предметная область.

## Telegram MVP: волны 1–5

Первые пять технических волн проверяют ядро платформы на отдельной стартовой нише: автономный Telegram-сервис для русскоязычных специалистов и создателей — маркетологов, дизайнеров, разработчиков, предпринимателей и контент-команд.

**Цель:** автоматически выпускать три качественных поста в день — утром, днём и вечером.

```text
Источники выбранной ниши
          ↓
Кандидаты и дедупликация
          ↓
Оценка пользы и проверяемости
          ↓
Контентный пакет + разрешённый визуал
          ↓
Очередь публикаций
          ↓
Telegram
```

Для первой ниши пост публикуется только если он даёт аудитории практическую ценность. Реклама, партнёрские материалы, вакансии, явная нерелевантность и технические релизы без понятного кейса остаются в журнале с объяснением, но не попадают в следующий этап.

## Архитектурные принципы

| Принцип | Что это значит |
|---|---|
| **Качество до квоты** | Если подходящих материалов недостаточно, система фиксирует дефицит, а не публикует слабый контент. |
| **Объяснимые решения** | У каждого кандидата есть источник, оценка, статус и причина отказа. |
| **Идемпотентность** | Повтор задачи не создаёт дублирующий пост. |
| **Модульность** | Ниши, источники, генераторы, форматы и площадки подключаются через независимые адаптеры. |
| **Конфигурация, а не хардкод** | Ниша, ЦА, язык, источники, промпты, форматы, расписание и площадки принадлежат ферме. |
| **Себестоимость под контролем** | Дешёвые фильтры работают раньше LLM; тяжёлая генерация доступна только лучшим кандидатам. |
| **Честный roadmap** | В README отмечено, что уже работает, а что является целью следующих волн. |

## Контентный конвейер

Postify не хранит «бесконечный склад материалов». Он ведёт компактный реестр решений:

- кандидаты получают начальное объяснимое решение до AI-анализа;
- возраст материала сохраняется как сигнал, а не создаёт отказ сам по себе;
- отклонённые кандидаты сохраняют минимальный след для дедупликации и анализа качества источника;
- опубликованные темы защищают канал от повторов.

Ссылка на первоисточник не добавляется механически. Она появляется в посте, только если помогает читателю: открывает сервис, демо, инструкцию или конкретный следующий шаг.

## Интеллектуальный слой: тренды → контент → результат

Postify задуман не как планировщик публикаций. Его задача — находить сигналы в большом потоке контента, понимать, что может зацепить конкретную аудиторию, и превращать это в формат, рассчитанный на удержание и действие.

```text
Публичные сигналы: видео, посты, обсуждения, поисковые темы
                              ↓
Кластеры трендов, паттерны виральности и ранние сигналы интереса
                              ↓
Оценка: тема × аудитория × формат × площадка
                              ↓
Хук, сценарий, визуальная подача и CTA
                              ↓
Метрики удержания, вовлечённости, кликов и конверсии
                              ↓
Обратная связь в следующие решения генератора
```

В Telegram MVP этот слой начинается с оценки пользы и качества кандидатов. Позднее он расширится до кроссплатформенного анализа трендов и виральности.

## Панель управления контентными фермами

Пользователь сможет создавать независимые контентные фермы: с собственной нишей, источниками, каналами, форматами, голосами, промптами и правилами автопостинга. Аналитика покажет не только общий охват, а причинно связанную картину результата.

| Вопрос | Что показывает система |
|---|---|
| Что растёт? | Охваты, подписчики, вовлечённость, клики и конверсия по каждой ферме и каналу. |
| Что залетает? | Темы, тренды, конкретные посты и ролики с аномально сильным результатом. |
| Какой формат работает? | Длина, хук, темп, тип демонстрации, голос, визуальная подача, CTA и площадка. |
| Где результат теряется? | Просадка удержания, слабый CTA, неудачный визуал, неподходящий источник или аудитория. |
| Что масштабировать? | Лучшие связки «источник → алгоритм → формат → площадка → аудитория». |

## Очерёдность Telegram MVP

| Волна | Результат |
|---|---|
| **01 — импорт** | Выбранный источник, кандидаты, PostgreSQL и идемпотентный `run-once`. |
| **02 — отбор** | Универсальные дешёвые правила и неизменяемый журнал решений. |
| **03 — контент** | Пакет текста и визуала после выбора генератора, ключа и политики прав. |
| **04 — Telegram** | Реализованы очередь, три слота и идемпотентная публикация. |
| **05 — наблюдаемость** | Долговечный журнал и расширенный `status` по созданным сущностям. |

После стабилизации Telegram MVP развиваются независимый видеосервис, дистрибуция и UI. Видеосервис не зависит от Telegram: Telegram-пост — только один из возможных входов для универсального видеобрифа.

## Что готово в волнах 1–2

- конфигурация из `.env` и переменных окружения;
- импорт кандидатов из HN Algolia;
- PostgreSQL-хранилище и Alembic-миграции;
- команды `run-once`, `start`, `status`, `stop`;
- systemd service и timer для запуска импорта по расписанию.
- универсальный профиль отбора из переменных окружения: версия, язык, аудитория, правила, маркеры и окно свежести;
- объяснимые решения `selected` и `rejected`, которые сохраняются один раз и не перезаписываются;
- `run-once` сначала импортирует кандидатов, затем отбирает все записи без решения и сообщает оба набора счётчиков.

`run-once` извлекает текст выбранных статей, создаёт не более трёх локальных контентных пакетов и оставляет их на проверке. Используются локальный Codex и изображения статьи или Wikimedia Commons; Telegram, UI и генерация изображений не входят в эту волну. Для проверки доступны `postify content list`, `show ID`, `approve ID` и `reject ID`.

## Подготовка

Нужны Python 3.12+, `uv` и отдельный экземпляр PostgreSQL 16 для Postify. Не используйте общий экземпляр PostgreSQL, если команда `postify stop` не должна иметь право его останавливать.

```sh
uv sync --all-groups
test -e .env || cp .env.example .env
```

Заполните в `.env` как минимум `DATABASE_URL`, `HN_QUERY`, параметры systemd, расписания и все `SELECTION_*` из `.env.example`. Профиль отбора не привязан к одной нише: правила и маркеры задаются конфигурацией. Не добавляйте `.env` в Git.

Примените миграции к той же отдельной PostgreSQL 16:

```sh
POSTIFY_ALEMBIC_DATABASE_URL='postgresql+psycopg://<пользователь>:<пароль>@<хост>:5432/<база>' \
  uv run --env-file .env alembic upgrade head
```

`POSTIFY_ALEMBIC_DATABASE_URL` передаётся Alembic явно; команда не берёт URL миграций из другого источника.

## Запуск

```sh
uv run --env-file .env postify run-once
uv run --env-file .env postify publish-once
uv run --env-file .env postify start
uv run --env-file .env postify status
uv run --env-file .env postify stop
```

`run-once` выводит счётчики импорта, проверенных кандидатов, `selected`, `rejected` и конкурентных конфликтов. `publish-once` доставляет один approved пакет; для него нужны только `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` и `TELEGRAM_TIMEOUT_SECONDS`. `start` включает отдельные import и Telegram timers, а `stop` ждёт завершения обоих one-shot services.

`status` показывает систему, сущности, последние пакеты и попытки доставки, дневной план, последние запуски и проблемы. Для `status` не нужны Telegram credentials: команда не вызывает Telegram и только читает PostgreSQL и безопасные systemd facts.

Telegram preflight с реальными credentials остаётся pending: UI, аналитика и видеосервис остаются следующими волнами.

## Установка systemd units

Скрипт устанавливает system units. Для `/etc/systemd/system` нужны соответствующие права.

```sh
sh scripts/install-systemd.sh \
  --project-dir /абсолютный/путь/Postify \
  --env-file /абсолютный/путь/Postify/.env \
  --python /абсолютный/путь/Postify/.venv/bin/python \
  --user <системный-пользователь> \
  --group <системная-группа> \
  --timezone Europe/Moscow \
  --destination /etc/systemd/system \
  --on-calendar 'Mon..Fri *-*-* 09:00:00' \
  --on-calendar 'Mon..Fri *-*-* 14:00:00' \
  --on-calendar 'Mon..Fri *-*-* 19:00:00'
```

Три `--on-calendar` остаются расписанием import timer. Отдельный publish timer читает только `TELEGRAM_ON_CALENDAR_MORNING`, `TELEGRAM_ON_CALENDAR_DAY` и `TELEGRAM_ON_CALENDAR_EVENING` из указанного `.env`; parser не исполняет содержимое файла. Скрипт проверяет оба набора расписаний и все units до установки.
