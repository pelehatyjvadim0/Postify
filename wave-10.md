# Wave 10: ручное управление Postify без автоматических квот

## Контекст для исполнителя

Эту волну нужно реализовать в уже существующем worktree Postify:

- путь: `/home/user/Рабочий стол/Postify/.worktrees/ui-v1-html-mockup`;
- ветка: `feature/ui-v1-html-mockup`;
- исходный HEAD на момент записи: `9a499cb`;
- из этого worktree поднят локальный UI на `http://127.0.0.1:8000`.

В worktree уже есть незакоммиченные изменения: Codex content analyzer, Pydantic-схема ответа, профиль `gpt-5.6-luna/high`, Telegram-проверка, UI каналов, повторные анализы и созданные медиа. Их нельзя сбрасывать, перезаписывать или обходить новой веткой. Нужно продолжить работу поверх текущего состояния.

Этот документ описывает только изменения Postify. SSSF, ADW и их quality-gates в Wave 10 не входят.

## Проблема

Сейчас дневные лимиты, предназначенные для фоновой автоматизации, также блокируют ручную работу владельца в UI. После создания трёх пакетов нельзя запросить новые варианты без ручного изменения лимитов или БД.

Цель Wave 10: ручные действия владельца в UI не должны расходовать или проверять автоматические квоты. Владелец не должен бегать в настройки и сбрасывать счётчики.

## Два режима выполнения

Все операции, запускающие pipeline, должны получить серверный execution context:

```text
execution_mode = automatic | manual
actor = scheduler | ui
```

### Automatic

Автоматические запуски планировщика продолжают учитывать:

- `daily_analysis_limit`;
- `daily_package_limit`;
- пропорции fresh/reserve;
- окна retry;
- расписание поиска и публикации;
- дневной план и дефицит.

### Manual

Действия, явно запущенные владельцем из UI:

- не проверяют дневные квоты анализов и пакетов;
- не расходуют автоматические квоты;
- не ждут слота расписания;
- могут начать retry сразу, без ожидания автоматического retry-окна;
- всегда попадают в журнал с `mode=manual` и `actor=ui`.

Режим и bypass нельзя слепо доверять полю JSON от клиента. UI-endpoint должен выбирать manual-policy на серве; scheduler — automatic-policy.

## UI: «Подобрать ещё 3 поста»

Внизу экрана «Проверка» добавить кнопку:

```text
Подобрать ещё 3 поста
```

По нажатию:

1. UI создаёт ручную операцию дозагрузки.
2. Backend берёт следующие ещё не обработанные материалы.
3. Codex анализирует их моделью и reasoning effort из настроек проекта.
4. Создаётся до трёх новых пакетов.
5. Для выбранных пакетов подбирается медиа.
6. UI ожидает завершения операции и обновляет список без полной перезагрузки страницы.

Три пакета — размер одной партии, а не дневной лимит. Кнопку можно нажимать повторно.

Если текущие пакеты ещё не разобраны, UI должен попросить сначала одобрить или отклонить видимые пакеты. Отклонённые пакеты остаются в истории, но не засоряют активную очередь проверки.

Состояния кнопки:

- default: `Подобрать ещё 3 поста`;
- running: `Анализируем материалы…`, повторное нажатие заблокировано;
- no candidates: `Новых материалов нет. Запустите новый поиск.`;
- failure: безопасная причина и кнопка повтора;
- unresolved review: понятная подсказка, какие пакеты ещё требуют решения.

## Ручные операции без бизнес-квот

Единая manual-policy должна применяться ко всем ручным «пинкам» владельца:

1. **Новый поиск.** Импортировать и отобрать новые материалы по ручному запросу.
2. **Подобрать ещё 3 поста.** Взять следующую партию материалов и создать до трёх пакетов.
3. **Повторить анализ.** Немедленно повторить упавший Codex-анализ, не дожидаясь retry-окна.
4. **Перегенерировать пост.** Создать новую версию текста для конкретного материала или пакета.
5. **Заменить медиа.** Повторно подобрать изображение без перезапуска всего pipeline.
6. **Опубликовать сейчас.** Не ждать слота расписания и дневного плана.
7. **Повторить отправку.** Ручной командой повторить retryable-доставку.
8. **Вернуть в анализ.** Повторно обработать отклонённый материал.

Все эти операции должны использовать общие application services и repository-гарантии. Нельзя создавать дублирующий «ручной pipeline» рядом с автоматическим. Различаться должна policy квот и запуска, а не сама бизнес-цепочка.

## Обратная связь и версии

При отклонении пакета UI должен позволять указать причину, например:

- слишком технично;
- неинтересная тема;
- слабый заголовок;
- слишком много общих слов;
- не подходит аудитории;
- нужен другой формат;
- свободный комментарий.

Причина хранится в истории. При ручной дозагрузке или перегенерации накопленные причины могут передаваться Codex как обратная связь, но только в безопасном, структурированном виде.

Повторный анализ и перегенерация не должны удалять предыдущие попытки или подменять их в БД. Нужна явная история попыток/версий, при этом повтор из UI не ограничивается автоматической квотой.

## Метрики и журнал

Ручные и автоматические счётчики нужно разделить. Ручные операции не должны увеличивать счётчик, по которому scheduler блокирует следующий автозапуск.

Минимально в UI и API нужно уметь показать:

```text
Автоматические анализы: 12 / 12
Ручные анализы: 18

Создано автоматически: 3 / 3
Создано вручную: 6
```

В журнале для ручной операции нужно хранить и выводить:

- источник `ui`;
- режим `manual`;
- тип операции;
- модель Codex и reasoning effort, если операция вызывала Codex;
- сколько материалов было взято;
- сколько пакетов создано;
- терминальный статус и безопасный failure code.

Ручные запуски не должны сами по себе создавать `analysis_limit_reached`, `package_limit_reached` или ложный дефицит автоматики.

## Технические гарантии, которые не снимаются

Manual-mode отключает только бизнес-квоты и ожидание расписания. Он не отключает:

- Pydantic-валидацию схемы Codex;
- `--output-schema` для Codex CLI;
- timeout и безопасные failure codes;
- защиту от дублей;
- идемпотентность;
- запрет параллельного запуска двух одинаковых операций для одного проекта;
- проверку канала Telegram и прав бота;
- защиту от повторной отправки;
- проверку `message_id` после публикации;
- проектную изоляцию;
- журнал операций и историю статусов.

Три пакета за один клик остаются ограничением размера партии для управляемости UI, но не дневной квотой.

## API-контракт

Для дозагрузки нужен явный mutation endpoint. Рекомендуемый контрак:

```text
POST /api/v1/projects/{project_id}/packages/load-more
```

Успешный ответ:

```json
{
  "status": "accepted",
  "requested": 3,
  "operationRunId": 5
}
```

Операция должна выполняться через тот же operation runner, что и текущие `run-once`/`publish-once`: accepted не означает completed, а UI должен дождаться терминального статуса журнала.

Конкретные URL остальных ручных операций можно выбрать в плане реализации, но они должны быть resource-oriented, project-scoped, CSRF-защищёнными и не принимать от клиента недоверенный `bypass_quotas`.

## Критерии готовности

Wave 10 завершена, когда:

1. Scheduler по-прежнему строго соблюдает дневные лимиты.
2. Кнопки UI запускают manual-mode и не читают/не увеличивают автоматическую квоту.
3. После трёх созданных пакетов владелец может ручную подобрать следующие три, не изменяя config и БД.
4. Новые пакеты появляются в «Проверке», имеют медиа и открываются в detail view.
5. Несколько быстрых нажатий не создают параллельные дубли операций и пакетов.
6. Ручные retry, regenerate, media replacement, publish-now, delivery retry и return-to-analysis работают без автоматических квот, но сохраняют все технические гарантии.
7. Автоматические и ручные метрики и журнал разделены.
8. Ручная активность не порождает ложные `analysis_limit_reached`, `package_limit_reached`, `unknown_persisted_state` или фиктивный success.
9. Новые migration, API, application, repository и UI-потоки покрыты регрессионными тестами.
10. Текущие Codex-, Telegram-, scheduler-, publication- и project-isolation-гарантии остаются зелёными.

## Обязательные тесы Postify

Нужно добавить или обновить тесты, которые доказывают:

- automatic-run останавливается на дневном лимите;
- manual-run проходит при уже исчерпанном automatic-лимите;
- manual-run не увеличивает automatic-счётчик;
- load-more создаёт не более трёх пакетов за один запуск, но разрешает последующие ручные партии;
- два одновременных load-more не дублируют анализы/пакеты;
- неразобранная review-очередь даёт понятный API/UI-ответ;
- отсутствие кандидатов не записывается как ложный success с созданными пакетами;
- модель и effort в ручном Codex-запуске взяты из project configuration;
- схема Codex по-прежнему передаётся в `--output-schema` и валидируется Pydantic v2;
- история попыток/версий не теряется при manual retry/regenerate;
- manual publish-now обходит расписание, но не обходит Telegram-проверки и идемпотентность;
- dashboard и journal разделяют manual/automatic метрики;
- browser-flow проверяет default/running/success/empty/error/unresolved состояния кнопки и появление новых пакетов.

## Порядок реализации

1. Ввести execution context и quota-policy в application layer.
2. Разделить persistence и метрики manual/automatic migration-ами.
3. Перевести scheduler на явную automatic-policy без изменения его поведения.
4. Перевести текущие UI-мутации на manual-policy.
5. Добавить load-more use case и API.
6. Добавить UI-кнопку, polling операции и обновление review-списка.
7. Добавить остальные ручные операции через общие application services.
8. Обновить dashboard, journal и safe status taxonomy.
9. Добавить целевые unit/integration/browser regressions.
10. Проверить один реальный ручной проход после исчерпания automatic-лимита: UI -> Codex -> новые пакеты -> detail view.

## Вне объёма Wave 10

- любые изменения SSSF/ADW;
- замена Codex на другого AI-провайдера;
- отключение схемы или доменной валидации Codex-ответа;
- отключение Telegram-проверок, защиты от дублей или идемпотентности;
- автоматическое одобрение или публикация пакетов без решения владельца.
