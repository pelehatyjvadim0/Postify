## Цель Wave 3: целевое состояние S_n+1

Wave 3 создаёт контентные пакеты для выбранных кандидатов, но **не публикует**
их в Telegram и не реализует UI. Telegram-очередь и публикация — Wave 4.

```text
selected
  → очередь обработки
  → извлечение текста исходной статьи
  → AI-анализ 12 тем
  → до 3 контентных пакетов с локальным изображением
  → awaiting_review / approved / rejected
```

В каждом пакете должны быть достаточные для проверки данные: исходный URL,
извлечённый контекст, результат анализа, текст поста, локальный путь к
визуалу, его внутренний источник и история статусов. В Telegram-пост не
добавляется ссылка на первоисточник, но URL хранится внутри системы для
проверяемости.

## Согласованные продуктовые решения

### AI

- Генератор текста: локальный Codex через подписку ChatGPT.
- На целевой машине допускается `codex exec`; перед приёмкой нужен живой
  preflight этого запуска. Точное публичное имя модели/режима («Luna») не
  хардкодить до проверки фактически доступной команды.
- Codex получает не только title/snippet HN: Postify загружает исходную статью
  и извлекает её основной текст.
- Цель текста: практическая новая информация для русскоязычной аудитории;
  жёсткий шаблон поста не требуется.

### Очередь и лимиты

Новые настройки должны быть конфигурацией, не хардкодом:

```text
CONTENT_DAILY_ANALYSIS_LIMIT=12
CONTENT_DAILY_PACKAGE_LIMIT=3
CONTENT_PRIORITY_FRESHNESS_DAYS=14
CONTENT_FRESH_SHARE_PERCENT=90
CONTENT_RESERVE_SHARE_PERCENT=10
```

- За сутки Codex анализирует максимум 12 кандидатов `selected`.
- Из них он выбирает максимум 3 наиболее релевантные темы и создаёт для них
  контентные пакеты.
- Кандидаты, найденные за последние 14 дней, — свежий приоритет; более старые
  — резерв. Их не удалять и не переводить в `rejected` только из-за возраста.
- Распределение должно быть точно 90/10 на длинной дистанции. При дневном
  лимите 12 это не постоянные 11/1: нужен накопительный quota/credit механизм.
  За пять дней: 54 свежих и 6 резервных кандидатов.
- Кандидат, начавший AI-обработку, не должен снова попасть в суточные 12;
  итог одной попытки фиксируется отдельно от неизменяемого selection decision.

### Статьи и повторная попытка

- Для технически недоступной статьи, которая уже была `selected`, назначать
  одну отложенную повторную попытку через 6 часов.
- Не делать отдельный фоновый таймер: пользователь запускает систему вручную.
  Каждый `postify run-once` поднимает due retries, если `retry_at <= now`.
- Retry входит в лимит 12 анализов суток.
- Если повторная попытка также завершилась технической ошибкой, фиксировать
  терминальный технический результат, сохранять кандидата и историю, но не
  повторять бесконечно.

### Визуал

Приоритет получения изображения:

```text
og:image / twitter:image исходной статьи
  → подходящее изображение, найденное в материале
  → тематический поиск через Wikimedia Commons API
```

- Изображение **не** генерируется AI.
- Выбранный файл скачивается в локальное временное хранилище Postify; не
  оставлять лишь внешнюю hotlink-ссылку.
- После успешного подтверждения публикации Telegram (это уже Wave 4) файл
  удаляется немедленно.
- При ручном отклонении пакета файл также удаляется.
- Нужна уборка зависших временных файлов старше 48 часов при запуске.
- Проверять как минимум MIME-тип, размер и безопасное имя/путь файла.

### Ручная проверка

Закладывается фундамент для будущего UI. Wave 3 обязана дать CLI-способ
просмотреть пакет и принять решение.

```text
not_started → processing → awaiting_review → approved
                          ↘ rejected / failed
```

- По умолчанию сгенерированный пакет попадает в `awaiting_review`.
- Нужны CLI-команды/эквивалентные операции просмотра, approve и reject.
- Если в будущем для фермы выключена ручная проверка, пакет после генерации
  автоматически получает `approved` и будет ждать Telegram-очереди Wave 4.
- Wave 3 не должна включать Telegram API, очередь публикаций или фронтенд.

## Обязательный Development Loop 0.4

Следовать `docs/development-loop/README.md` без сокращений:

1. Сначала зафиксировать Wave 3 как атомарный переход `S_n → S_n+1`:
   спецификация, границы, конкретные файлы, риски, критерии приёмки,
   доказательства и mutation gates.
2. Sol 5.6 High готовит RED-пакет **без рабочего кода**, трассировку
   требований, причины RED и карту неверных реализаций.
3. Проверить, что RED вызван отсутствующим поведением, а не сетью, Codex,
   PostgreSQL или неустановленной зависимостью.
4. Terra 5.6 Medium реализует минимальный код до GREEN.
5. Свежая Terra 5.6 High независимо проверяет сначала тесты и мутации, затем
   код. Critical/Important возвращают работу в fix-loop.
6. Выполнить живую проверку доступных внешних границ, merge в `main`, полный
   GREEN уже на `main`, очистку артефактов и подтверждение чистого Git.
7. Создать запись `docs/development-loop/runs/YYYY-MM-DD-run-NNN.md` с eval,
   возвратами, bottleneck и решениями перед следующим вейвом.

Критичные mutation gates Wave 3 должны доказывать как минимум:

- нельзя анализировать больше 12 и создать больше 3 пакетов;
- 90/10 соблюдается накопительно, а не приблизительно;
- один кандидат не обрабатывается повторно и конкурентный запуск не создаёт
  дубль;
- статья не анализируется лишь по title/snippet;
- due retry поднимается при ручном запуске после 6 часов, но не раньше;
- review-required не обходится, auto-review ведёт к `approved`;
- медиа не удаляется до успешного подтверждения Telegram, но удаляется при
  reject и по TTL-уборке;
- ошибки Codex, сети, извлечения и файловой системы не раскрывают секреты и
  оставляют согласованное восстанавливаемое состояние.

## Границы и предосторожности

- Не отправлять изменения в GitHub без отдельного запроса пользователя.
- Не использовать настоящий Codex/сеть в автотестах; внешние границы должны
  иметь подменяемые адаптеры. Реальный `codex exec` — отдельный ручной
  preflight/живое доказательство, после подтверждения оператором
- Не менять неизменяемую модель `selected/rejected` Wave 2 ради жизненного
  цикла контентного пакета: это отдельная сущность/состояние.
- Не добавлять генерацию изображений, Telegram-публикацию, UI и аналитику в
  этот вейв.
- Существующие `SELECTION_FRESHNESS_DAYS=30` относятся к Wave 2 и не должны
  неявно заменять отдельный 14-дневный приоритет контентной очереди.
