# UI v1 — подключение backend и настройки проекта

Дата: 2026-08-12.

## Цель

Заменить демонстрационные данные HTML-мокапа реальными данными Postify, открыть
существующие действия backend через HTTP API и добавить компактный интерфейс
пользовательских настроек проекта.

Первая версия остаётся однопользовательской и обслуживает один активный проект.
Модель данных и API используют идентификатор проекта, чтобы следующие версии
могли добавить несколько проектов без смены основных контрактов.

## Продуктовые границы

В рабочий UI входят семь разделов:

1. обзор;
2. материалы;
3. проверка;
4. очередь;
5. публикации;
6. журнал;
7. настройки проекта.

Аналитика и генерация видео не входят в эту версию. Интерфейс не показывает
фиктивные метрики или неработающие действия. Архитектура допускает будущие
форматы контента и платформы доставки.

## Выбранный подход

Postify получает встроенное HTTP-приложение на FastAPI. Оно предоставляет JSON
API и раздаёт production-версию утверждённого интерфейса «Тёплая студия».
Команда `postify ui` запускает приложение локально на `127.0.0.1` по умолчанию.

Пользовательская конфигурация хранится в PostgreSQL. Переменные окружения
остаются источником инфраструктурных параметров: адреса БД, системных unit,
каталогов, сетевых таймаутов и ключа шифрования секретов. Первый запуск создаёт
проект из текущей безопасной конфигурации окружения.

Новый обязательный `POSTIFY_SECRET_KEY` содержит Fernet-ключ. Если ключ не
настроен, чтение интерфейса остаётся доступным, но сохранение или использование
секретов канала завершается безопасной конфигурационной ошибкой.

HTTP-слой не повторяет доменную логику. Команды API вызывают существующие
application actions, а чтение экранов выполняет отдельный query-сервис с
типизированными представлениями.

## Универсальная модель подключений

### Проект

`ContentProject` хранит название, тему, язык, аудиторию, часовой пояс, профиль
отбора, правила генерации и выбранные CTA. Все новые рабочие сущности получают
`project_id`; существующие данные мигрируют в созданный проект по умолчанию.

### Источник

`SourceConnection` описывает подключаемый источник:

- `provider` — стабильный код адаптера;
- `name` — пользовательское название;
- `enabled` — участвует ли источник в импорте;
- `configuration` — проверенная провайдером JSON-конфигурация;
- `schedule` — расписание получения материалов.

В этой версии работает провайдер `hn_algolia`. Его параметры: поисковый запрос,
теги и число материалов. Название Hacker News не попадает в общие контракты,
таблицы проекта или элементы интерфейса, относящиеся ко всем источникам.

Добавление другого источника требует нового адаптера и схемы его конфигурации,
но не изменения проекта, экранов материалов или сценария импорта.

### Канал

`ChannelConnection` описывает площадку доставки:

- `provider` — код адаптера;
- `name` — пользовательское название;
- `enabled` — доступен ли канал для маршрутизации;
- `configuration` — несекретные параметры провайдера;
- `secret` — зашифрованные реквизиты;
- `connection_status` — результат последней проверки.

В этой версии работает провайдер `telegram`. API никогда не возвращает токен:
клиент получает только признак наличия секрета. Пустое поле при редактировании
сохраняет действующий токен, а отдельное действие удаляет подключение.

### Формат, маршрут и CTA

`ContentFormat` отделён от канала. Первая реализация содержит текстовый формат
«Практический разбор B», и его настройки не ссылаются на Telegram.

`CallToAction` хранит пользовательский текст и режим использования ссылки.
CTA можно назначить проекту по умолчанию либо переопределить в маршруте.

`PublicationRoute` связывает формат, канал и CTA. Поэтому будущий видеопакет
можно направить в один или несколько добавленных каналов без изменения модели
генерации. В первой версии активен один текстовый маршрут в один канал.

## Хранение и историчность

Миграция создаёт таблицы проектов, источников, форматов, CTA, каналов и
маршрутов. `project_id` добавляется к кандидатам, решениям, попыткам, пакетам,
доставкам, дневным квотам и журналу запусков. Существующие записи получают ID
проекта по умолчанию, после чего ограничения уникальности становятся
проектными.

Провайдерские таблицы доставки переименовываются в общие `deliveries` и
`delivery_attempts`; конкретный адаптер определяется через канал и маршрут.
Пакет сохраняет снимок темы, аудитории, формата и CTA, применённых при
генерации. Доставка сохраняет маршрут и снимок канала. Изменение настроек не
переписывает историю старых решений и публикаций.

Импорт загружает все включённые источники проекта через реестр адаптеров и
суммирует результаты по единому контракту. Ошибка одного источника сохраняется
в журнале и не маскирует результаты остальных источников.

## Пользовательские настройки

Экран настроек состоит из компактных секций с кратким итогом. Одновременно
раскрыта только выбранная секция; редкие технические параметры находятся в
блоке «Дополнительно».

### Основное

- название проекта;
- тема;
- язык;
- аудитория;
- часовой пояс.

### Источники

- список подключений и их состояние;
- добавление источника из каталога поддерживаемых провайдеров;
- включение и отключение;
- параметры и расписание конкретного провайдера.

### Аудитория и отбор

- окно свежести;
- правила рекламы, нерелевантности, найма и технического релиза без пользы;
- тематические, исключающие и практические маркеры;
- версия политики изменяется системой при сохранении.

### Генерация и форматы

- дневной лимит анализа;
- дневной лимит пакетов;
- доли свежего и резервного контента;
- приоритетная свежесть;
- обязательность ручной проверки;
- выбранный текстовый формат и его читаемое описание.

Формат B задаёт хук, простое объяснение ценности, компактные возможности,
механику при необходимости, аудиторию, ограничение и полезный следующий шаг.
Эта инструкция передаётся анализатору вместе с темой, языком и аудиторией.

### CTA

- название;
- текст действия;
- режим ссылки: без ссылки, полезная ссылка на источник или заданный URL;
- URL для соответствующего режима.

### Каналы и маршруты

- список каналов;
- подключение Telegram через chat ID и токен;
- безопасная замена или удаление токена;
- включение канала;
- выбор формата, CTA и канала для маршрута публикации.

### Расписание

- расписание получения материалов;
- утренний, дневной и вечерний слоты публикации;
- включение автопубликации;
- явное отображение часового пояса.

### Дополнительно

Пользователь может менять таймаут анализа и предельные размеры статьи и медиа.
Адрес БД, каталог медиа, systemd ownership и ключ шифрования в UI не выводятся.

## Подключение существующих экранов

### Обзор

Использует эксплуатационный snapshot: найденные кандидаты, решения, пакеты,
готовые доставки, публикации за день, дефицит, сигналы и последние операции.

### Материалы

Показывает реальные кандидаты и решения: источник, ссылка, время, статус,
причину, сигналы и версию политики. Оценка не показывается, потому что backend
её сейчас не хранит.

### Проверка

Показывает реальные контентные пакеты и медиа. Действия approve/reject вызывают
существующий `ReviewContent`. Причина пользовательского отклонения сохраняется
в истории пакета.

### Очередь

Показывает approved-пакеты, состояния доставки и три настроенных слота.
До резервирования доставка остаётся прогнозом очереди, а не изображается как
уже назначенная публикация.

### Публикации

Показывает Telegram-доставки и попытки: исход, код, объяснение, внешний message
ID и время подтверждения. Название экрана и фильтры используют общие термины
«канал» и «публикация»; Telegram отображается как провайдер записи.

### Журнал

Показывает operation runs, состояние БД и планировщика, эксплуатационные
сигналы и причины дефицита. Запуск импорта и одиночной публикации доступен как
явная команда с блокировкой повторного параллельного запуска.

## HTTP API

Все маршруты находятся под `/api/v1`:

- `GET /bootstrap` — проект, доступные провайдеры и сводка интерфейса;
- `GET /projects/{project_id}/dashboard` — обзор и эксплуатационный статус;
- `GET /projects/{project_id}/materials` — кандидаты и решения;
- `GET /projects/{project_id}/packages` — контентные пакеты;
- `GET /projects/{project_id}/packages/{package_id}` — пакет с историей;
- `POST /projects/{project_id}/packages/{package_id}/approve`;
- `POST /projects/{project_id}/packages/{package_id}/reject`;
- `GET /projects/{project_id}/queue`;
- `GET /projects/{project_id}/publications`;
- `GET /projects/{project_id}/operations`;
- `POST /projects/{project_id}/operations/run-once`;
- `POST /projects/{project_id}/operations/publish-once`;
- `GET /projects/{project_id}/settings`;
- `PUT /projects/{project_id}/settings/{section}`;
- CRUD `/projects/{project_id}/sources`;
- CRUD `/projects/{project_id}/channels`;
- CRUD `/projects/{project_id}/ctas`;
- CRUD `/projects/{project_id}/routes`;
- `POST /projects/{project_id}/channels/{channel_id}/check`.

Ответы используют стабильные коды состояний. Русские подписи принадлежат
frontend и не хранятся как доменные значения.

## Выполнение задач и расписание

Команды из UI запускаются через тот же application-слой, что и CLI. Долгий
`run-once` выполняется в фоне; API отвечает `202`, а UI обновляет журнал. Один
проект не может иметь два одновременных запуска одного типа.

Локальный планировщик читает активные расписания из PostgreSQL и использует
PostgreSQL advisory lock, чтобы только один экземпляр создавал запуск. Старые
systemd timers остаются совместимым CLI-режимом, но при работе web-планировщика
должны быть отключены, чтобы не создавать конкурирующие расписания.

## Безопасность

- сервер по умолчанию слушает только `127.0.0.1`;
- первая версия не заявляет многопользовательскую авторизацию;
- токены шифруются ключом из окружения и никогда не возвращаются через API;
- ошибки API не содержат DSN, токены, локальные пути и тексты исключений;
- медиа выдаётся только по ID пакета после проверки принадлежности проекту;
- URL источников остаются кликабельными, но backend не проксирует произвольные
  пользовательские URL.

## Состояния frontend

При старте UI загружает `/bootstrap`, затем данные выбранного экрана. Каждый
раздел имеет состояния загрузки, пустого результата, ошибки и повторной
загрузки. После мутации frontend перечитывает затронутые ресурсы вместо
оптимистичного изменения нескольких несогласованных списков.

Если backend недоступен, интерфейс не возвращается к демонстрационным данным.
Он показывает понятную ошибку подключения. Демо-сброс удаляется из production
UI.

## Проверка

- unit-тесты доменных настроек, провайдерских схем и шифрования секретов;
- integration-тесты миграции, project scope, CRUD и исторической конфигурации;
- API-тесты сериализации, ошибок, секретов и переходов approve/reject;
- component-тесты FastAPI с PostgreSQL и реальными query-репозиториями;
- browser-тесты семи разделов, форм, загрузки, ошибок и обновления после команд;
- retained-тесты CLI и пяти существующих волн;
- проверка wheel: API и статические ресурсы работают вне checkout;
- адаптивная проверка на 360, 768 и 1440 пикселях.

## Критерии готовности

- семь разделов работают на данных backend без демонстрационного fallback;
- все существующие действия доступны из UI и сохраняют прежние доменные
  инварианты;
- пользовательские настройки действительно влияют на последующие импорты,
  отбор, генерацию и маршрутизацию;
- общие модели не содержат HN- или Telegram-специфичных полей;
- секрет канала не появляется ни в одном GET-ответе или пользовательской
  ошибке;
- новый источник, канал или формат можно добавить отдельным адаптером;
- полный набор тестов проходит с отдельной PostgreSQL 16;
- изменения не отправляются в GitHub и не сливаются без подтверждения.
