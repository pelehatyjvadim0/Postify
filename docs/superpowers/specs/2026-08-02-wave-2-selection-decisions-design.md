# Wave 2: отбор кандидатов и журнал решений

## Цель

Добавить дешёвый, объяснимый и идемпотентный отбор перед AI-анализом. Механизм работает для любой контентной ниши и не знает о Hacker News, AI-тематике или конкретной аудитории.

`selected` означает допуск к будущему AI-анализу, а не готовность к публикации. `rejected` означает окончательный отказ по текущей версии политики. Статуса `reserve` нет.

## Продуктовые решения

Кандидат отклоняется только по явно доказанной причине:

1. реклама или партнёрский материал;
2. материал явно вне настроенной ниши;
3. вакансия, найм или объявление;
4. технический релиз без понятного пользовательского сценария.

Недостаток данных не является причиной отказа. Если по заголовку и доступным сигналам нельзя уверенно доказать нарушение, кандидат получает `selected`.

Свежесть не является жёсткой причиной отказа. Настраиваемое окно свежести формирует сигнал для следующего этапа. Для будущих AI-партий согласовано стартовое значение профиля: 90% основной ёмкости отводится свежим материалам, 10% — материалам старше окна. Это значение не зашивается в код и позднее регулируется через UI. Старая публикация может пройти дальше, если остаётся полезной и практичной. Лимит AI-партии и доля старых материалов появятся в рабочей конфигурации вместе с AI-потребителем; Wave 2 не создаёт неиспользуемую очередь.

Приоритет будущей AI-партии определяется пользой для аудитории:

1. соответствие настроенной аудитории и нише;
2. признаки практического применения;
3. свежесть;
4. проверяемость;
5. нормализованные сигналы источника только как дополнительный критерий.

Метрики конкретного источника, например `points` и `num_comments` Hacker News, не входят в доменную политику.

## Универсальный профиль отбора

Продуктовые параметры принадлежат профилю фермы, а не коду:

- версия политики;
- язык и описание аудитории;
- включённые правила отказа;
- тематические включения и явные исключения;
- маркеры рекламы, найма, технических релизов и практического применения;
- окно свежести.

В Wave 2 профиль поступает из внешней конфигурации. Позднее UI будет изменять тот же контракт без изменения доменной логики. В коде остаются только технические инварианты: допустимые статусы и причины, проверка диапазонов, идемпотентность и стабильный порядок.

Правила отказа включаются независимо. Например, ферма с вакансиями может отключить отказ по найму. Отсутствие тематического совпадения само по себе не доказывает нерелевантность; для отказа нужен настроенный явный отрицательный сигнал.

## Архитектура

Wave 2 сохраняет модульный монолит и текущие направления зависимостей:

```text
CLI → сценарий run-once → импорт → сценарий отбора → порты
                                      ↓
                              доменная политика

PostgreSQL-репозитории → порты + домен
```

Доменная политика является чистой и детерминированной. Она получает кандидата, профиль и текущее время, затем возвращает черновик решения с кодом причины и наблюдаемыми сигналами. Она не читает окружение, не выполняет SQL и не разбирает поля конкретного источника.

Сценарий отбора:

1. загружает кандидатов без решения;
2. применяет одну версию профиля ко всему запуску;
3. сохраняет новые решения одной транзакцией;
4. сообщает число `selected`, `rejected` и конкурентно пропущенных решений.

Сценарий `run-once` сначала завершает импорт, затем отбор. Если процесс остановился между этапами, следующий запуск подберёт кандидатов без решения. Временное отсутствие решения — техническое аварийное состояние, а не бизнес-статус.

## Модель решения

Для каждого кандидата хранится не более одного первоначального решения:

- кандидат;
- статус `selected` или `rejected`;
- стабильный машинный код причины;
- краткое объяснение;
- JSON-набор использованных сигналов;
- версия политики;
- время решения.

Для `selected` используется причина `eligible_for_ai`. Для отказов используются отдельные коды рекламы, нерелевантности, найма и технического релиза без применения.

Решение неизменяемо. Повторный или конкурентный запуск не перезаписывает его. Переоценка после изменения профиля потребует отдельного явного сценария и не входит в Wave 2.

Таблица решений имеет внешний ключ на кандидата, уникальность по кандидату и ограничения допустимых статусов. Наблюдаемые сигналы сохраняются для объяснимости, но исходные данные кандидата не дублируются.

## Ошибки и транзакции

- Некорректный профиль отклоняется до чтения и изменения решений.
- Ошибка загрузки кандидатов или записи решений завершает `run-once` ненулевым кодом.
- Пакет решений фиксируется атомарно; при ошибке выполняется явный rollback.
- Конкурентная вставка того же решения считается идемпотентным конфликтом, а не ошибкой.
- Уже сохранённые результаты импорта не откатываются при последующей ошибке отбора: следующий запуск продолжает с кандидатов без решения.
- В пользовательский вывод не попадают traceback, содержимое кандидатов или конфигурационные словари.

## Конфигурация без UI

До появления сущности фермы и UI профиль задаётся переменными окружения с валидацией Pydantic. `.env.example` содержит только безопасные примеры, не привязанные к AI-нише. Пустые обязательные наборы, неизвестные коды правил, неположительное окно свежести и дубли после нормализации считаются ошибкой конфигурации.

Wave 2 не создаёт собственный DSL правил. Профиль имеет явную типизированную схему, которую будущий UI сможет сохранять и передавать приложению.

## Проверка

### Домен

- каждая включённая явная причина создаёт ожидаемый отказ;
- отключённое правило не влияет на решение;
- недостаток данных и title-only кандидат получают `selected`;
- старый кандидат не отклоняется только из-за возраста;
- профиль другой ниши меняет решение без изменения кода;
- нормализация регистра и пробелов детерминирована;
- объяснение и сигналы соответствуют фактически сработавшему правилу.

### Приложение

- обрабатываются все кандидаты без решения;
- одна версия профиля применяется ко всему запуску;
- счётчики результата точны;
- импорт выполняется до отбора;
- ошибка отбора не отменяет завершённый импорт;
- повторный запуск подбирает кандидатов, оставшихся без решения после сбоя.

### PostgreSQL и CLI

- миграция создаёт ограничения и откатывается вниз;
- повторная и конкурентная запись создаёт ровно одно решение;
- пакет фиксируется атомарно, ошибка вызывает явный rollback;
- решения переживают закрытие session;
- `run-once` показывает счётчики импорта и отбора;
- ошибки конфигурации и БД дают ненулевой код без traceback;
- wheel содержит новую миграцию и находит Alembic head вне checkout.

## Mutation gates

Перед проверкой production-кода тесты обязаны покраснеть при каждой мутации:

1. заменить консервативный `selected` для недостаточных данных на `rejected`;
2. сделать возраст самостоятельной причиной отказа;
3. включить отключённое правило;
4. подменить профиль одной ниши терминами другой;
5. удалить одну из четырёх причин отказа;
6. читать HN-специфичное поле в доменной политике;
7. не сохранять код причины, сигналы или версию политики;
8. разрешить второе решение для кандидата;
9. перезаписывать существующее решение при повторе;
10. удалить commit либо явный rollback репозитория;
11. выбирать только кандидатов текущего импорта вместо всех без решения;
12. запустить отбор до импорта;
13. скрыть ошибку отбора и завершить CLI кодом 0;
14. потерять новую миграцию при сборке wheel.

## Не входит в Wave 2

- вызов AI и окончательная оценка полезности;
- фактическое формирование AI-партий 90/10;
- генерация текста и визуала;
- публикация и защита от повторов тем;
- UI и хранение профиля фермы в БД;
- переоценка уже принятых решений;
- универсальный язык пользовательских правил.

Эти границы не разрешают хардкодить будущие значения. Они откладывают их подключение до появления работающего потребителя.
