# Wave 4 — доставка в Telegram

Дата: 2026-08-09.

## Переход

- `Sₙ`: `main@2bd0c90` создаёт и вручную одобряет контентные пакеты, но не
  доставляет их во внешнюю систему.
- `Sₙ₊₁`: три настраиваемых ежедневных слота атомарно выбирают только
  `approved` пакет, публикуют сохранённый текст и локальное медиа в один
  Telegram-канал, сохраняют подтверждённый `message_id` либо объяснимый исход
  без автоматического риска дубля.

## Границы

В Wave 4 входят очередь Telegram-доставки, три слота, Telegram Bot API adapter,
идемпотентный scheduled run, журнал попыток, подтверждение публикации и
безопасное удаление локального медиа после подтверждения.

Не входят UI, форматы текста, тематики, аналитика, другие площадки,
универсальный outbox и исправления известных дефектов Wave 3, если они не
блокируют доказательство доставки.

## Архитектура

Доставка получает отдельный application action и узкие порты репозитория и
Telegram publisher. Action владеет выбором пакета, состояниями, классификацией
ошибок и политикой повторов. Adapter владеет только Telegram HTTP-протоколом,
multipart-запросом и преобразованием ответа в типизированный результат.

Долговечные данные хранятся отдельно от `content_packages`:

- одна запись доставки на пакет, защищённая уникальностью `package_id`;
- append-only попытки с номером, временем, исходом и безопасной причиной;
- внешний `message_id`, время подтверждения и время удаления медиа;
- состояние `pending`, `sending`, `retryable`, `published`, `failed` или
  `uncertain`.

Один запуск слота в транзакции выбирает старейший `approved` пакет через
`FOR UPDATE SKIP LOCKED`. Пакет с существующей активной, подтверждённой,
неопределённой или терминально неуспешной доставкой повторно не резервируется.
Конкурентные запуски не могут получить один пакет.

## Поток

1. Scheduler вызывает отдельную команду публикации в одном из трёх значений
   `OnCalendar`, заданных конфигурацией, а не кодом.
2. Repository резервирует не более одного `approved` пакета и фиксирует
   `sending` до внешнего вызова.
3. Adapter читает сохранённые `post_text`, `media_path` и MIME, затем вызывает
   Telegram Bot API для публикации текста с локальным медиа.
4. Только успешный Telegram-ответ с целочисленным `message_id` считается
   подтверждением.
5. Repository атомарно сохраняет `message_id`, попытку, `published` и переводит
   пакет `approved → published`.
6. После этого media provider удаляет ровно подтверждённый локальный файл.
   Ошибка cleanup не отменяет публикацию и повторяется без нового Telegram
   вызова.

Пустой слот завершается успешно без изменения пакетов. Ошибка импорта или
генерации не должна блокировать отдельную команду публикации.

## Идемпотентность и неопределённый исход

Telegram Bot API не принимает клиентский idempotency key. Поэтому строгий
автоматический повтор после timeout, разрыва соединения или падения процесса в
состоянии `sending` мог бы создать дубль.

Политика Wave 4:

- локальная ошибка до начала HTTP-запроса и явный Telegram `ok=false` могут
  стать `retryable` либо `failed` по типизированному коду;
- timeout, transport error после начала запроса, потерянный ответ и найденный
  при старте stale `sending` переходят в `uncertain`;
- `uncertain` никогда не ретраится автоматически и не переводит пакет в
  `published`;
- повторный запуск не вызывает Telegram для `published`, `failed` или
  `uncertain` доставки;
- причина ошибки не содержит token, полного URL Bot API или содержимого
  локального файла.

Так система сохраняет обещание «подтверждённая доставка или объяснимый исход
без автоматического дубля», не заявляя недоказуемую exactly-once семантику.

## Конфигурация и эксплуатация

Окружение задаёт bot token, channel/chat ID, timeout и три расписания. Token
исключается из логов и сообщений ошибок. Конфигурация валидируется до обращения
к БД или сети. Существующий контентный формат не меняется.

Systemd получает отдельные service/timer для команды `publish-once`, поэтому
доставка не зависит от успеха import/selection/content.
Installer проверяет ровно три календарных выражения и сохраняет rollback
существующих unit-файлов.

## Доказательства

RED-пакет обязан доказать:

- выбор только `approved`, FIFO и один пакет на слот;
- три конфигурируемых ежедневных слота;
- конкурентный claim без дублей;
- точный Telegram multipart contract для текста и локального медиа;
- сохранение `message_id` и истории каждой попытки;
- отсутствие `published` без подтверждения;
- отсутствие автоматического ретрая после `uncertain` и stale `sending`;
- повторный запуск после `published` не вызывает adapter;
- media delete только после committed confirmation;
- rollback при ошибках БД и повтор cleanup без новой публикации;
- отсутствие token в ошибках;
- migration upgrade/downgrade и wheel/install границы.

После hermetic GREEN свежая Terra 5.6 High выполняет мутации и review до нуля
Critical/Important. Затем разрешённый live preflight публикует специально
одобренный тестовый пакет реальным adapter, сверяет сохранённый `message_id`,
повторным запуском доказывает отсутствие дубля и подтверждает удаление медиа.
Без реальных Telegram credentials Wave 4 остаётся на стадии preflight pending и
не сливается в `main`.

После принятия выполняются merge в `main`, полный повторный gate, удаление
worktree/ветки и генерируемых кэшей, проверка чистого Git и запись eval запуска.

## Оркестрация

Один 5.6-sol оркестратор держит границы Wave 4. Он передаёт Sol 5.6 High только
RED-тесты, трассировку и карту мутаций; Terra 5.6 Medium — минимальный GREEN;
свежей Terra 5.6 High — независимую проверку тестов, мутаций и затем кода.
Wave 5 получает нового оркестратора только после полного завершения Wave 4.
