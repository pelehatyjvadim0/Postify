# План удаления наследия Postify

Дата: 05.09.2026. Основание — принятый пользователем локальный AutoPostTG
на localhost:8000 и инспекция текущего рабочего дерева. Этапы 1–6 завершены;
результаты проверок и резервные копии записаны в `cleanup-progress.md`.
Git-фиксация ожидает корпоративные имя/email автора.
Новая инструкция пользователя отменяет прежнее правило README «безвредное оставить».

## Эталон и подтверждённые зависимости

- Три вкладки: «Посты», «Подключения», «Настройки». В постах сохраняются список,
  календарь, фильтры стадий, карточка, оригинал, повтор подготовки, переписывание,
  принятие/отклонение, назначение даты и канала, ошибки и история действий.
- `workspace.js:loadWorkspace` получает packages, materials, publications, settings,
  queue. Эти API нужны, даже если их прежние отдельные экраны больше не нужны.
  Ссылка «История действий» ведёт на действующий `#journal`.
- В работающем контейнере прочитаны только CONTENT_ANALYZER и CONTENT_MODEL:
  `codex`, `gpt-5.6-terra`. Codex сохраняем. Gemini — отдельный уже реализованный
  адаптер целевого сценария из README; автоматически не удаляем и не переключаем.
- Источник Telegram, сессия аккаунта, курсор чтения, дедупликация и отправка ботом
  входят в рабочий контур. Интерфейс заменяемого источника сохраняем.
- «Скоро» относится к настройке автоматического расписания. Отправка одобренного
  поста в назначенное редактором время остаётся рабочей функцией.
- Подключения сейчас показывают формат и правило публикации. Удаление каталога
  форматов или переход с route_id на channel_id меняет эталон; в эту вырезку
  не включаем. CTA уже скрыт, но `ProjectRuntimeGraph.effective_generation`
  продолжает выбирать CTA, включая fallback, и передавать его генератору.
- `SelectCandidates` пропускает текстовые материалы, но для других ещё вызывает
  старый отбор. `SqlAlchemyContentRepository.claim` даже в mvp_mode обращается
  к таблицам дневного использования и квот. Это действующие зависимости.
- `SqlAlchemyDashboardRepository` обслуживает карточки, материалы, план и историю.
  Удалить весь модуль по названию dashboard нельзя. Аналогично журнал операций
  используется выполнением задач и восстановлением планировщика.

## Порядок работ и минимальные тесты

Одна итерация — один связанный срез, отдельный русский коммит после проверки.
Сначала тест на требуемое поведение, подтверждённое падение по нужной причине,
затем изменение и зелёный тест. Для сохраняемого поведения сначала фиксируем
проходящий тест эталона; красную фазу не изображаем искусственно.

### 0. Зафиксировать эталон перед удалением

Рабочее дерево содержит большой незакоммиченный MVP. Сначала сохранить принятую
итерацию в новом GitLab с корректными корпоративными авторскими данными; ранее
запрошенные имя/email ещё не получены. Не смешивать её с последующей вырезкой.
Перед миграциями сохранить БД отдельно от Git и проверить восстановление в
изолированной БД. Секреты, сессию Telegram и медиа в репозиторий не добавлять.

Переиспользовать существующие `test_mvp_pipeline.py`, `test_mvp_plan_delivery.py`,
`test_mvp_source_storage.py`, `test_telegram_account_ingestion.py` и `test_codex_mvp.py`.
UI-тесты сначала сверить с текущим интерфейсом: часть проверяет уже скрытые поля.

Добавить один браузерный регрессионный сценарий с заполненными данными: открыть
конкретный пост, переключить календарь → подключения, задержать ответ старого
запроса и завершить его после нового. Проверить заголовок подключений и конкретное
имя канала; затем настройки → посты и тот же пост. Запуск на desktop и mobile.

### 1. Удалить старые экраны и неиспользуемые пользовательские команды

В `web/static/app.js`, `screens.js`, `api.js`, `styles.css` удалить старые рендереры
overview/materials/review/queue/publications и их недостижимые загрузчики после
проверки ссылок. Общие форматтеры и badges из screens.js остаются. Старые hash-ссылки
можно сохранить как короткие переходы на стадии workspace без старых рендереров.
Журнал сохраняется.

Из API/services/manual_operations удалить команды прежнего UI без потребителя:
«подобрать ещё 3», publish-now, публичный publish-once и замену картинки через
Wikimedia. Перед каждым удалением проверить вызовы, включая CLI и фоновые задачи.
Внутреннюю адресную отправку планировщика и retry доставки сохранить.
Удалить только агрегаты старого обзора, сохранив используемые запросы репозитория.

Тесты: заполненный workspace показывает конкретный пост в нужной стадии и дате;
снятый GET endpoint возвращает 404/not_found, снятые POST — 405/http_error
(поведение существующего роутера и static mount без специальных заглушек); новый поиск
запускает одну операцию и показывает её конечный результат. Публичный publish-once
и внутренняя отправка проверяются раздельно, чтобы удаление API не отключило план.

### 2. Вырезать CTA из исполнения и контракта настроек

Исторический snapshot генерации сохранять как историю, не применять повторно.

Тесты: проект с ранее сохранённым CTA «Подпишись на старый канал» и тоном
«Кратко, спокойно» отправляет обоим адаптерам точный ожидаемый brief с темой,

Сохранение правила с конкретным форматом и каналом и генерация проходят без CTA.
Проверять структурированные поля запроса, не весь промпт большим snapshot.

### 3. Удалить старый входной конвейер и отбор

Удалить HN adapter и регистрацию, HN-настройки/seed, HTTP article extractor,
article retry, selection policy и словари признаков. Сохранять текст материала
и передавать его в подготовку напрямую. Сначала заменить зависимость claim от
candidate_decisions; затем удалить SelectCandidates, decision repository/port
и старые поля конфигурации. Материалы и их идентичность остаются.

Тесты: конкретный старый текст с рекламным/вакансионным словом всё равно попадает
в генерацию и даёт ожидаемый пост awaiting_review; повтор того же внешнего ID
в том же подключении возвращает тот же материал и одну генерацию; одинаковый ID
в двух подключениях даёт две независимые записи. Использовать существующие тесты
дедупликации, не дублировать их на всех слоях. Невалидный вход должен дать точный
код ошибки и соответствующий статус материала, не сетевой поиск статьи.

### 4. Убрать квоты и раздвоение mvp/legacy

Удалить дневные продуктовые квоты, fresh/reserve credits, ранжирование по свежести,
старые счётчики обзора, legacy ProcessContent и ветки mvp_mode. Рабочий сценарий
становится единственным. Убрать review_required как переключатель, сохранив
обязательное решение редактора.

Размер одной пачки, timeout модели и лимиты сетевых данных сохранить как технические
ограничения. Сейчас daily_analysis_limit также определяет размер пачки в mvp_mode:
при удалении сохранить его рабочее значение отдельным техническим параметром.
Не превращать удаление дневной квоты в неограниченный запрос к модели.

Тесты: при исчерпанном старом дневном счётчике три заданных материала обрабатываются
пачками 2 и 1 с точными ID без потери; созданный пост имеет awaiting_review;
повторный запуск не создаёт второй пост из завершённой попытки. Отдельно сохранить
регрессию блокировок: два конкурентных обработчика не забирают один материал.

### 6. Удалить остатки схемы БД

После прекращения всех обращений удалить новыми Alembic-миграциями таблицы/колонки
CTA, решений отбора, квот и ненужные JSON-поля конфигурации. Точный набор утвердить
по оставшимся SQL, FK и цепочке миграций. Не обнулять старые миграции и не менять
namespace postify массово: это отдельная косметическая задача.
Форматы, routes, материалы, попытки, посты, доставки, курсоры Telegram, операции
и задания остаются. Существующие тексты, планы, результаты и идентификаторы
сохраняются. Старые активные задания требуют явного завершения/преобразования,
чтобы удалённый тип операции не завис после рестарта.

Тесты миграции: заполнить БД материалом, постом, принятым планом, опубликованной
доставкой и курсором; после upgrade проверить те же ID, текст, UTC-время,
message_id и позицию чтения. Проверить upgrade на чистой БД отдельно.
Никаких delete/drop на рабочей БД до проверки на восстановленной копии.

## Правила точности тестов

- Один тест защищает один риск; общая фикстура небольшая, с осмысленными ID,
  текстом, каналом и фиксированным временем.
- Не принимать `assert result`, `assert items`, `assert not items`, «не упало»,
  один HTTP 200 или поиск слова в исходнике как доказательство поведения.
- Проверять конкретное состояние, данные, адресата, время, число вызовов и код
  ошибки. Нулевое число отправок до одобрения — содержательная проверка безопасности,
  если fixture содержит готовый к отправке пост и проверяется его точный статус.
- Для изменяемого поведения показать RED на старом коде и GREEN после изменения.
  Сохраняемые инварианты защищать существующими проходящими тестами; для рискованной
  регрессии проверить чувствительность временной точечной поломкой в тестовой копии.
- Мокать внешние Telegram/AI, фиксировать часы. SQL, миграции и конкурентную
  отправку проверять настоящей тестовой PostgreSQL, отдельно от эталонной БД.
- Удалять тесты снятых возможностей вместе с кодом. Сохранять проверки CSRF,
  изоляции проектов, защиты секретов/сессий, URL и путей файлов там, где эти
  механизмы продолжают использоваться.

## Завершение

Короткий сквозной сценарий: сообщение → подготовленный пост → ручной план →
одобрение → одна отправка в срок → подтверждённый message_id в UI.
Сохранить существующие проверки: без одобрения/раньше срока не отправляется;
просроченный принятый пост отправляется после рестарта; uncertain не повторяется.
Проверки выполняются на тестовых данных с подменой внешних сервисов; реальная
публикация для чистки не требуется. После каждого UI-этапа — проверка оператором.

В ходе этой инспекции проверены исходники, HTML/OpenAPI работающего сервиса и
выбранный AI-провайдер контейнера. Браузерные сценарии и тестовый набор не запускались.
Оценка сроков и выигрыша производительности не выполнялась.
