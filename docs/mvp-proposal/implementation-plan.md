# План достижения Telegram MVP

Основание: `Telegram-MVP-для-согласования.pdf`, 2 страницы, 7 критериев.
Дата: 05.09.2026. Проверены код AutoPostTG/Postify `22d4739` и FakeTG `b3989c46`.
Это план реализации. Приложения, базы и remote не изменялись; runtime-проверки не выполнялись.

## 1. Направление реализации

Использовать существующие Python/FastAPI, PostgreSQL, SQLAlchemy/Alembic и HTML/JS UI.
Оставить одно приложение с существующим планировщиком. Не вводить React, Celery,
Redis, брокер событий, общую БД с FakeTG или отдельную платформу интеграций.

Основной объём: подключить заменяемый адаптер источника (первый — Telegram-группа),
передать материалы в отдельную подготовку русского текста через Gemini, закрепить дату за конкретным предложением,
связать модерацию с этим планом и ограничить отправку принятым постом в его срок.
Очистку выполнять небольшими изменениями вокруг рабочего сценария. Массовое удаление
общих моделей и переписывание миграций до первого сквозного результата замедлит работу.
Это инженерная оценка; сроки и производительность не измерялись.

## 2. Зафиксированные решения и открытые вопросы

Уточнение пользователя 05.09.2026: MVP размещается на облачном VPS; после простоя
сервис автоматически отправляет просроченные принятые посты без ограничения
опоздания. Неопределённый результат уже начавшейся отправки (`uncertain`) не
повторяется автоматически. Локальный Docker — контур разработки и проверки.

Подтверждено пользователем: первый источник — Telegram-группа с арабскими постами,
но источник должен быть заменяемым адаптером. Общая логика не зависит от Telegram,
конкретной группы или арабского языка. Адаптер получает материал; отдельный этап
Gemini переводит и подготавливает русский текст по настройкам проекта. Полноценную
систему автоперевода не строим. Дату и время задаёт
редактор вручную; в следующей версии FakeTG генерирует изображения для наших постов.
Автоматическое распределение по слотам не реализуем. Это уточняет формулировку PDF
о назначении даты системой: система сохраняет выбранное редактором время.

| Вопрос | Почему влияет на реализацию |
|---|---|
| Идентификатор группы, способ доступа и начальная глубина загрузки | Источник выбран; до подключения нужно определить доступ и загрузку: только новые сообщения или также заданная история. Способ чтения не выбирать до проверки доступа. |
| Формат: текст или текст с обязательной картинкой? | Сейчас без изображения пакет не завершается; доставка использует только sendPhoto. PDF не требует обязательного изображения. |
| Как редактор получает доступ: локально/закрытая сеть или интернет? | В Postify нет полноценной пользовательской авторизации; CSRF-проверки её не заменяют. Для публичного доступа нужен отдельный согласованный минимум защиты. |
| URL нового репозитория и перенос истории? | Нужны перед настройкой push; текущий origin указывает на Postify. |
| Выборка и порог качества текста? | Критерий 7 требует оценки редактора; автоматические тесты не подтверждают «человечность». |

Рекомендации для согласования: один редакторский контур;
один пост отправляется в один канал. Пока эти решения не подтверждены,
зависимые ветки плана остаются условными.

Gemini 3.8 Flash и идентификатор `gemini-3.8-flash` подтверждены
[официальной документацией Google](https://ai.google.dev/gemini-api/docs/latest-model?hl=en).
Перед реализацией проверить доступ с ключом выбранного проекта. Название модели
больше не является неизвестным; ключ, лимиты и качество на наших материалах ещё не проверены.

## 3. Что сохранить, убрать и упростить

Последнее решение пользователя заменяет предыдущий список кандидатов на удаление:
неиспользование само по себе не является причиной удаления. Менять или удалять только
то, что нарушает критерии MVP, делает ненужные настройки обязательными, запускает
лишние операции или мешает смене источника. Для каждого такого изменения фиксировать
конкретное препятствие. Если достаточно отключить зависимость в сборке приложения,
не удалять весь модуль. Безвредные сущности и функционал оставить; последующая очистка
не является обязательством следующих версий.

| Элемент | Действие в новом проекте |
|---|---|
| `domain/content`, `application/content/review_content.py` | Сохранить жизненный цикл и модерацию; обязательное одобрение обеспечить на backend. |
| `application/delivery`, `sqlalchemy_delivery.py`, Telegram adapter | Сохранить блокировки, попытки, message_id и uncertain; изменить выборку по конкретному плану. |
| `application/scheduling`, `sqlalchemy_schedule.py` | Переиспользовать устойчивые задания; публикацию связать с постом и временем, а не FIFO одобренных пакетов. |
| PostgreSQL, Alembic, project_id, каналы | Сохранить. Не менять БД на SQLite ради совпадения со стеком FakeTG. |
| Шифрование токенов, ограничения HTTP/файлов, CSRF | Сохранить везде, где соответствующий ввод и загрузка остаются. |
| `web/static` и JSON API | Переиспользовать дизайн и клиент. Основные экраны: «Посты», «План», «Настройки»; ошибки и история — в карточке/простом журнале. |
| Codex adapter и настройки reasoning | Исключить обязательность Codex для запуска и генерации нового контура. Изолированный неиспользуемый адаптер и его тесты оставить, если они не мешают. |
| `review_required=false`, обход расписания через publish-now/publish-once | Убрать из пользовательского MVP и закрыть backend-обходы обязательной модерации/времени. Нельзя ограничиться скрытием кнопок. |
| `deploy/systemd`, `scripts/install-systemd.sh`, управление PostgreSQL из CLI | Не запускать второй планировщик и не останавливать внешнюю БД из нового контура. Неиспользуемые скрипты оставить, если они не влияют на запуск MVP. |
| `justfile` SSSF, `.superpowers`, старые wave/spec/evidence-артефакты, `ui-mockup` | Не делать их зависимостью запуска/сборки. Безвредные файлы и связанные проверки не удалять ради уборки. |
| «Обзор», показатели квот, технические настройки отбора, каталог CTA/форматов | Не требовать заполнения лишних настроек для MVP. Остальные экраны, каталоги и таблицы оставить, если они не нарушают новый сценарий. |
| HN Algolia, HN-настройки и парсер статей | Убрать обязательность HN/статьи для других адаптеров. Сам HN-адаптер и извлечение статей сохранить, если они изолированы и не мешают. |
| Отбор, квоты свежести и ingestion | Отключить для нового контура фильтры/квоты, мешающие обработке сообщений. Переиспользовать импорт и дедупликацию; связанные таблицы не удалять автоматически. |
| Wikimedia и получение картинок из статей | Не требовать поиск картинки для обработки материала из другого источника. Изолированный провайдер и общий файловый слой сохранить, если они не мешают выбранному формату. |
| Старые тесты | Удалить только тесты удалённого поведения. Сохранить проверки модерации, доставки, изоляции, миграций и используемой безопасности. |

Не переименовывать весь Python namespace `postify` первым этапом: название продукта,
README и адрес репозитория можно заменить отдельно без массового изменения импортов.
Не обнулять миграции существующей БД. Для нового сервиса использовать отдельную БД;
наследуемую цепочку сначала проверить на чистом экземпляре.

## 4. Порядок реализации

### Этап 0. Отдельный проект и воспроизводимый запуск

1. После получения адреса подготовить отдельный checkout/репозиторий. Если выбрана
   работа в другой ветке здесь — использовать `.worktrees` по AGENTS.md.
2. Не переносить `.env`, ключи, БД и локальные медиа. Учесть некоммитированный
   `docs/mvp-proposal/`: обычный clone его не перенесёт.
3. Настроить новый origin явно. До первого push проверить fetch/push URL;
   в исходный Postify не пушить. Историю не переписывать без выбранного режима переноса.
4. Поднять отдельную БД и UI, зафиксировать минимальную базовую проверку миграций,
   карточки и модерации. Определить один рабочий способ запуска.

Результат: новая копия открывает UI, использует свои данные и секреты.
Технический префикс пакета и старые связанные таблицы не мешают этому этапу.

### Этап 1. Адаптер источника → Gemini → предложение в UI

1. Переиспользовать `application/ports/candidate_source.py` и реестр источников,
   минимально уточнив контракт для получения текста материала без обязательной статьи.
   Первый адаптер разместить в `adapters/sources/telegram_group.py`. Группа и доступ
   задаются конфигурацией. Скрипт, если потребуется, только запускает общий импорт;
   логика Telegram остаётся в адаптере, перевод — в Gemini-этапе.
2. Реализовать один Gemini adapter за `application/ports/content_analyzer.py`;
   использовать имеющийся HTTP-клиент, если выбранный REST-контракт этого достаточно.
   При необходимости SDK добавить только его, без LLM-фреймворка.
3. Сохранять модель, версию промпта и результат генерации. Переименовать активные
   поля `codex_model` в нейтральные через последовательное изменение backend/UI/миграции.
4. Передавать тему, аудиторию, тон, фактический материал и ограничения формата.
   Проверять структурированный ответ; пустой/невалидный результат не становится постом.
5. Показать состояние генерации и ошибку. Повтор запроса/обновление страницы
   не должны создавать несколько предложений из одной операции.

Минимальный контракт и границы источника:

- Адаптер возвращает нейтральный материал: идентификатор подключения, внешний ID,
  исходный текст и, если доступно, ссылку/дату. Позиция чтения непрозрачна для общего
  контура и интерпретируется адаптером. Не проектировать поля для всех будущих источников.
- Исходный и целевой языки задаются настройками подготовки текста. Для первого
  подключения это арабский → русский; в source adapter и общем импорте нет такого хардкода.
  Перевод переиспользует Gemini adapter без отдельной платформы переводов.
- Сохранять оригинал и результат. Ключ дедупликации — проект + подключение источника
  + внешний ID. Telegram-адаптер сопоставляет группу и message_id этому контракту;
  общий контур не требует Telegram-полей. Повторный импорт не создаёт дубли.
- Передавать в UI русский текст. Сохранять смысл, имена, числа и факты источника;
  естественная русская подача не должна добавлять новые утверждения.
- При ошибке перевода сохранять понятный статус для повтора; исходное сообщение
  не терять и не выдавать за готовый русский пост. Одобрение редактора остаётся обязательным.
- До подключения уточнить группу, доступ, начальную историю и обработку вложений,
  если они нужны. Не обещать чтение истории/всех сообщений через имеющийся токен
  публикации и не добавлять пользовательскую Telegram-сессию без решения о доступе.
- Не реализовывать каталог языков, автоопределение языка, новые реальные адаптеры,
  отдельную очередь переводов или синхронизацию правок/удалений источника без запроса.

Проверка: adapter с подставным HTTP-ответом (успех, таймаут, отказ, неверный формат),
затем сообщение из выбранной группы → русский пост в UI. Повторный импорт не
дублирует пост; ошибка перевода допускает повтор без потери сообщения. Критерий 1;
для критерия 7 проверить также точность передачи арабского оригинала.
Проверка заменяемости: подставной адаптер с нетелеграмными идентификаторами проходит
тот же импорт → Gemini → UI без изменений модерации и доставки. Это проверка контракта,
а не реализация второго продуктового источника.

### Этап 2. Дата конкретного поста и решение редактора

1. Минимально расширить существующий пакет: запланированный момент UTC и связь с
   каналом/маршрутом до одобрения. До ввода редактором дата может отсутствовать;
   одобрение и отправка такого поста запрещены. Использовать имеющийся project_id и часовой пояс.
   Это новый бизнес-план поста, не поле `scheduled_for` общего задания планировщика.
2. Добавить ручной выбор даты и времени в карточке и сохранять его в БД. Проверять
   формат, часовой пояс и будущее время при сохранении и принятии. Автоподбор слотов
   и ограничение «один пост на слот» не добавлять: это не согласованные требования.
3. Вывести текст, канал, дату, время, часовой пояс и статус в «Постах» и «Плане».
   Время на экране должно читаться из сохранённого плана, а не вычисляться как прогноз.
4. Сделать модерацию обязательной для любого пути создания поста. Реализовать
   атомарные approve/reject с проверкой текущего статуса. Повторное нажатие безопасно.
5. Не добавлять редактирование текста/медиа после одобрения в MVP. Если остаётся
   регенерация, она создаёт результат для новой проверки и не наследует одобрение.
6. Отказ снимает пост с активного плана. Перенос, изменение канала и решение
   во время отправки обрабатываются согласованными переходами, а не прямым UPDATE.

Проверка: UI показывает закреплённый план до принятия; решения сохраняются после
перезагрузки; конфликтующие approve/reject не дают двух итогов. Критерии 2–4.

### Этап 3. План → Telegram → статус

1. Планировщик выбирает принятые посты, для которых наступило согласованное окно
   отправки, и создаёт долговечное задание с идентификатором конкретного поста.
2. Перед сетевым вызовом повторно проверить состояние, канал и дату в транзакции,
   атомарно зарезервировать отправку. Сохранить защиту от двух воркеров.
3. Сохранить message_id, попытку и результат. Показать их в карточке и плане.
4. Для текстового формата добавить sendMessage и сделать вложение необязательным.
   Если согласован обязательный визуал — переиспользовать sendPhoto. Проверять длину
   текста под выбранный способ отправки до одобрения, без молчаливого обрезания.
5. Реализовать согласованное поведение просрочки, рестарта и повторяемых ошибок.
   Таймаут после возможной отправки остаётся `uncertain`; автоматически не повторять.

Проверка: принятый пост выходит в выбранный канал в срок; отклонённый и ожидающий
не выходят; повторный tick, два обработчика и рестарт не дают повторной отправки;
ошибки и uncertain видны. Критерии 4–6.

Граница гарантии: после потери ответа нельзя одновременно гарантировать доставку
и отсутствие дубля слепым повтором. Сохраняем uncertain и явное разрешение ситуации.
Допустимую задержку относительно назначенного времени согласовать и измерить
на тестовом канале; не обещать точность до секунды без проверки.

### Этап 4. Очистка поставки и приёмка

1. Устранить только подтверждённые препятствия из раздела 3: обязательность старых
   настроек/провайдеров, обходы модерации и времени, конфликтующие запуски.
   Не выполнять массовое удаление старых сущностей БД, контрактов и модулей.
2. Для каждого удаления проверить импорты, bootstrap, конфигурацию, CLI, упаковку
   и прямые вызовы API. Не оставлять обязательные env-поля удалённых подсистем.
3. Проверить установку/запуск из чистой копии, миграции и весь короткий MVP-сценарий.
   Проверить доступ редактора в согласованной среде; не открывать локальный UI в интернет
   как будто в нём уже есть пользовательская авторизация.
4. Согласовать выборку для качества: предложение — 10 материалов и минимум 8 текстов
   без существенной правки, без фактических ошибок. Это предложенный порог, не принятое
   требование. Получить решение редактора; при провале доработать промпт.
5. Передать рабочий UI, инструкцию запуска, пример конфигурации без секретов и
   результаты семи проверок. Push выполнять только в подтверждённый новый remote.

После каждой видимой итерации передавать UI оператору. Проверять затронутую логику;
полный набор старых тестов и отдельный рефакторинг архитектуры не входят в критический путь.

## 5. Граница с FakeTG

Факты по коду FakeTG:

- `README.md` описывает StoryChat, генератор изображений вымышленных чатов.
- `android-renderer/renderer/api.py`: `POST /v1/render` принимает `application/zip`
  с RenderRequest и файлами, возвращает `image/png` либо ZIP нескольких страниц;
  `/health` проверяет рендерер. Есть ошибки 400/422/503/504/500.
- `tg-bot/.../rendering/client.py` уже реализует клиент; его входная модель
  включает сущности StoryChat, поэтому копирование клиента затянет соседнюю бизнес-логику.
- В `compose.yaml` Waydroid/ADB изолированы внутри сети; renderer не получает БД/токен бота.
  Не следует выставлять этот внутренний API в интернет для интеграции.

Что сохраняем в MVP без реализации интеграции:

1. Правила генерации, принятия и отправки остаются в application-слое,
   доступны из HTTP UI и не импортируют FakeTG.
2. Сохранить версионированный JSON API, идентификатор поста и разделение
   content analyzer / delivery adapter. Не передавать ORM-объекты через границу сервисов.
3. Если медиа входит в MVP, хранить вложение как принадлежащий AutoPostTG файл;
   UI не должен получать локальные пути. Не связывать бизнес-пост со схемой RenderRequest.
4. Не удалять общий HTTP/медиа слой как «ненужный Wikimedia», если он используется
   доставкой. Но и не строить новый media framework только ради будущего FakeTG.

Подтверждённый сценарий следующей версии:

- Для визуала FakeTG отдельный HTTP adapter преобразует согласованный сценарий
  в RenderRequest, принимает PNG/ZIP и сохраняет собственную копию. Текущий MediaProvider
  привязан к ExtractedArticle — его нельзя считать готовым универсальным интерфейсом.
  Расширять контракт только на этом этапе. Многостраничный результат требует решения
  о наборе вложений/альбоме; нельзя молча брать только первую страницу.
- AutoPostTG вызывает рендерер и получает изображения; вызов автопостинга из бота
  FakeTG не входит в выбранный сценарий. До интеграции отдельно определить, кто
  формирует сообщения вымышленного чата и его оформление. Это не решается обычной
  генерацией текста Telegram-поста и не входит в первую версию.

Пока не создавать FakeTG-таблицы, webhooks, общие модели, общую БД, роли,
Android-контейнеры и пустые адаптеры. Совместимость обеспечивается границами уже
существующих слоёв, а конкретный контракт запроса к рендереру оформляется в следующей версии.

## 6. Проверяемое завершение

| № из PDF | Доказательство |
|---|---|
| 1 | Арабский пост из выбранной Telegram-группы переведён через Gemini и сохранён как русское предложение в UI; повторный импорт не создаёт дубль. |
| 2 | Текст, канал, дата и время видны до принятия; после перезагрузки те же значения. |
| 3 | Принятие/отклонение сохраняется; повторные и конфликтующие действия безопасны. |
| 4 | Доставка не выбирает ожидающие/отклонённые посты ни через scheduler, ни через API. |
| 5 | Тестовый канал получает нужный пост по плану; повторные ticks и рестарт не создают дубль. |
| 6 | Успех, ошибка и неопределённый результат видны редактору. |

Критический путь: отдельная копия → заменяемый адаптер и доступ к выбранной группе →
подготовка русского текста через Gemini → предложение в UI → ручная дата и модерация →
адресная отправка → очистка и приёмка. До предоставления доступа к группе независимую
логику проверять на явно тестовых арабских сообщениях; это не заменяет приёмку реального источника.
Измерения длительности генерации, отправки и стоимости выполнять на сквозном сценарии;
календарную оценку до закрытия вопросов не фиксировать.

## 7. Параллельное исполнение

Требование пользователя: реализация ведётся параллельно, насколько позволяют
зависимости. Этапы выше описывают результаты, а не запрет одновременной работы.
Использовать до четырёх исполнителей: координатор и три агента.

### Старт: короткая общая подготовка

Координатор проверяет рабочее дерево, готовит новую рабочую копию и фиксирует
минимальные контракты материала, поста с ручной датой, статусов и ошибок API.
Согласовываются имена полей и примеры ответов — без предварительной реализации
всех слоёв. После этого сразу запускаются три независимых потока.

### Первая параллельная волна

| Исполнитель | Работа | Зона записи | Результат |
|---|---|---|---|
| Агент A: источник и Gemini | Заменяемый source adapter, Telegram-реализация, получение материала, перевод/подготовка текста, тесты ошибок и повторов | `adapters/sources`, `adapters/ai`, `application/ingestion`, `application/content/process_content.py`, соответствующие тесты | Материал проходит через согласованный контракт и превращается в русское предложение |
| Агент B: план и доставка | Ручная дата, обязательная модерация, адресные задания, транзакционная отправка, рестарт/uncertain | `infrastructure/database`, `infrastructure/repositories`, `domain`, `application/scheduling`, `application/delivery`, `application/content/review_content.py`, соответствующие тесты | Только принятый пост отправляется в назначенный канал по своей дате |
| Агент C: UI | Карточка предложения, дата/время, принять/отклонить, план и статусы | `web/static`, браузерные тесты | Видимый сценарий на подставных ответах согласованного API, затем на реальном backend |
| Координатор: сборка | Общие порты, конфигурация, HTTP API, сборка зависимостей и подключение результатов | `application/ports`, `config.py`, `bootstrap.py`, `web` кроме `static`, запуск и документация | Потоки соединяются в рабочий сценарий без дублирования реализаций |

Разделение применяется к конкретным файлам: если нужен чужой файл, исполнитель
передаёт запрос его владельцу. Новые файлы получают владельца до изменения.
Общие схемы и миграции не редактируются двумя агентами одновременно. Тестовые
каталоги делятся по затронутой логике; общие фикстуры меняет координатор.

### Что можно делать без внешних доступов

Источник проверяется на подставных сообщениях, Gemini — на контролируемых HTTP-ответах,
доставка — с тестовым publisher, UI — на согласованных JSON-данных. Отсутствие ключей
не останавливает эти задачи. Реальные доступы нужны для сквозной проверки, а не
для объявления тестового результата готовым продуктом.

### Зависимости и сборка

1. Общие контракты → одновременный старт A, B и C.
2. Миграция и операции сохранения из B → подключение A и реального API координатором.
3. Реальный API → переключение C с подставных данных и проверка редакторского сценария.
4. Доступы к группе/Gemini/каналу → реальное прохождение материала до публикации.
5. Рабочий сценарий → параллельные проверки источника, доставки и UI;
   затем одна итоговая проверка целой цепочки и оценка текста редактором.

Координатор подключает готовые части по мере появления, не ждёт окончания всей волны.
Каждый агент выполняет небольшую проверку своей логики и сообщает изменённые файлы,
результат и оставшиеся ограничения. Полный набор тестов всеми агентами не дублируется.

### Обязательный контроль тестов оркестратором

Оркестратор отвечает за подтверждение проверок. Сообщение исполнителя «тесты прошли»
само по себе не является доказательством и не позволяет принять задачу.

1. **Проверка смысла сразу после написания.** Каждый новый или изменённый тест
   сразу передаётся оркестратору либо независимому ревьюеру, который не писал этот
   тест и проверяемую реализацию. Не откладывать ревью до конца всей волны.
   Проверяющий читает тест вместе с затронутым кодом и связывает его с конкретным
   критерием MVP или необходимым для него инвариантом.
2. **Отсечение пустых проверок.** Не принимать тесты без значимых assertions,
   проверки констант/самих фикстур, подмену всей проверяемой логики моками,
   копирование реализации в ожидаемый результат, тесты выдуманного поведения
   или функционала вне scope. Моки внешних сервисов допустимы, если реальная
   прикладная логика остаётся под проверкой. Проверять наблюдаемый результат,
   изменение состояния или необходимое взаимодействие с внешним сервисом.
3. **Подтверждение чувствительности.** Для регрессии показать падение на исходном
   дефекте, когда это применимо. Для нового критичного инварианта проверить, что
   его намеренное нарушение приводит к падению теста. Такую проверку проводить
   изолированно, без изменения общего рабочего дерева параллельных исполнителей.
   Полный mutation-testing всего проекта не вводить.
4. **Свидетельство запуска.** Для каждой принятой проверки фиксировать точную команду,
   рабочую директорию, проверяемую ревизию или идентификатор снимка изменений,
   окружение (включая тестовую БД при необходимости), код выхода и фактический
   stdout/stderr с итогом passed/failed/skipped и количеством собранных тестов.
   Секреты в свидетельство не включать. Проверять, что нужные тесты действительно
   собраны и выполнены: отсутствие тестов, пропуск или xfail не подтверждают критерий.
5. **Независимый запуск.** Оркестратор или независимый ревьюер сам запускает новые
   и изменённые тесты на том же зафиксированном состоянии кода и сверяет результат
   с отчётом исполнителя. Для критичных проверок, закрывающих критерий MVP,
   оркестратор подтверждает результат повторным запуском на собранной версии.
   Это целевые проверки, а не повтор полного набора каждым агентом.
6. **Контроль актуальности.** Пока идёт запуск, другие исполнители не меняют
   проверяемые файлы и общие зависимости: использовать изолированный снимок либо
   согласовать короткое окно без записи в затронутые файлы. После влияющего изменения
   старый результат не засчитывать; связанные проверки повторить.
7. **Условия приёмки.** При несовпадении отчёта и вывода, слабом тесте или провале
   задача возвращается исполнителю. Нельзя удалять/ослаблять assertion, добавлять
   skip или менять ожидаемое поведение только ради зелёного результата.
   Исправленный тест снова проходит независимое ревью и запуск.

Оркестратор ведёт короткий журнал: задача/критерий → тесты → проверяющий →
снимок кода → команда и вывод → результат ревью → принято/возвращено.
Для состояния без коммита снимок определяется сохранённым diff и контрольными
суммами новых файлов; создавать коммит в текущем репозитории для этого не требуется.

Ревью и запуски выполняются по готовности небольших изменений. Остальные независимые
потоки продолжают работу. При четырёх занятых слотах ревью выполняет оркестратор
либо освободившийся агент, не участвовавший в проверяемой реализации; ожидание
отдельного пятого исполнителя не требуется. Внешние публикации и работу с общей
тестовой БД при этом координирует оркестратор.

### Ограничения ускорения

- Не выделять отдельного агента на массовую очистку: препятствия устраняет владелец
  затронутого потока. Безвредный функционал остаётся.
- Не распараллеливать изменения одной миграционной цепочки, операции с общей БД,
  изменение общих контрактов и итоговое решение о готовности.
- Не выполнять отправки в один тестовый канал несколькими независимыми исполнителями;
  реальные публикации координируются как часть одной проверки.
- Работа с Git следует отдельному решению о новом репозитории. Коммиты и push
  не выполняются в текущий remote; при создании отдельных веток использовать `.worktrees`.
- Выигрыш по времени не измерен: параллелизм ускоряет независимые части,
  но не заменяет интеграцию и проверку семи критериев.
