# Переработка AutoPostTG в SMM-агента — трейс задачи

Документ передаётся другому инстансу для детального планирования и реализации.
Он фиксирует **согласованные с заказчиком решения**, состояние кодовой базы и
предлагаемую декомпозицию. План работ здесь намеренно не расписан — его
составляет принимающий инстанс.

Дата фиксации: 11 сентября 2026.
Контракты API: [api-contract.md](api-contract.md).
Утверждённый мокап интерфейса: `ui-mockup/1-react-shadcn.html` (коммит `f09c549`,
ветка `ui-mockup-content-plan`).

---

## 1. Суть изменения

Продукт перестаёт быть переписчиком входящего потока и становится
**агентом-SMM-специалистом**.

Было: Telegram-группы → импорт материалов → AI переписывает материал → ревью →
публикация.

Стало: человек заполняет контент-план → агент по слоту плана пишет пост и
подбирает изображение из пула проекта → пост проходит слои проверок →
ревью или автопубликация.

Внешние источники контента исчезают. Источником истины для поста становятся
слот контент-плана и промпты.

## 4. Факты о текущем состоянии, влияющие на оценку

1. **Аутентификации пользователей нет.** Есть один общий пароль
   `POSTIFY_ACCESS_PASSWORD`, HMAC которого лежит в cookie
   (`web/app.py`, `web/security.py`). Таблицы пользователей не существует.
   Пароль и весь его контур удаляются, вход переезжает на Telegram-бота.
2. **Ни один из эндпоинтов не проверяет права.** Все методы принимают
   `project_id` и обслуживают его любому вошедшему.
3. **Подбора медиа нет вообще.** `MediaProvider` умеет только `delete` и
   `cleanup`. Поле `AnalyzedTopic.media_query` есть, но не используется:
   `process_content.py` всегда вызывает `complete_package(media=None)`.
4. **Промпты зашиты в код** — строка `instruction` внутри адаптеров.
   Пользовательских промптов в базе нет.
5. **Образ БД `postgres:17-bookworm` без pgvector.**
6. **Codex подключён как CLI через subprocess** (`codex_content_analyzer.py`),
   а не как HTTP API.
7. Gemini-адаптер существует, но `CONTENT_ANALYZER` по умолчанию `codex`, то
   есть на основном пути он не работал. Его контракт (`v1beta/interactions`)
   вживую не подтверждён.

## 5. Блокер, который надо закрыть до планирования медиа

**Codex CLI не умеет ни vision-подписи, ни эмбеддинги.** Он запускается как
процесс и возвращает текст. Решения Р4 и Р5 требуют:

- vision-вызова для подписи изображения при загрузке;
- модели эмбеддингов для подписи и поискового запроса.

Значит даже при рабочем провайдере Codex для медиа нужен **второй провайдер по
HTTP** — вероятнее всего Gemini API по уже существующему `GEMINI_API_KEY`.

Планирующему инстансу необходимо:
1. Подтвердить доступность конкретной модели эмбеддингов и vision-модели.
2. Зафиксировать поведение, когда ключ не задан: загрузка без подписи и без
   эмбеддинга, подбор изображения недоступен, явная ошибка в UI.

## 6. Модель данных

Новые таблицы:

- `users` — id, `telegram_user_id` (уникальный, строка), `telegram_username`,
  `display_name`, created_at, last_login_at, is_active. Паролей и почты нет.
- `login_requests` — `telegram_token` (43 символа base64url, уникальный),
  `browser_token` (уникальный), status (`pending` / `confirmation` /
  `approved` / `denied`), `telegram_user_id`, ip, created_at, expires_at,
  decided_at. TTL 10 минут.
- `user_sessions` — хеш токена, user_id, created_at, expires_at.
- `user_settings` — user_id, `common_prompt` (общий промпт на все проекты
  пользователя), updated_at.
- `app_settings` — одна строка, `system_prompt` уровня сервера.
- `content_plan_slots` — project_id, publish_at, rubric_id, topic, status,
  package_id, generate_at, created_at, updated_at.
- `media_assets` — project_id, путь к файлу, mime, размер, разрешение,
  caption, caption_model, embedding, uploaded_at, last_used_at, use_count,
  enabled.
- `media_usages` — asset_id, package_id, used_at.
- `project_rules` — project_id, текст правила, severity (`block` / `warn`),
  enabled, origin (`derived` / `manual`), порядок.
- `validation_reports` — package_id, iteration, layer, passed, details (jsonb).

Изменяются:

- `content_projects` — добавляются `owner_id`, `project_prompt`,
  `publication_mode`, `generation_lead_minutes`. Поля старого контура
  (`source_language` и прочие параметры импорта) удаляются.
- `content_packages` — `attempt_id` заменяется на `slot_id`, добавляются
  `media_asset_id`, `validation_passed`, `repair_iterations`.

Инфраструктура: образ БД меняется на `pgvector/pgvector:pg17`, добавляется
`CREATE EXTENSION vector`. Обе версии PG17, том должен подхватиться без дампа —
**ожидание, на проде не проверено**, перед деплоем нужен бэкап тома.

## 7. Три уровня промптов

Итоговый контекст генерации собирается строго в этом порядке:

1. **Системный промпт сервера** — общий для всех агентов всех пользователей.
   Им разработчики управляют поведением агента и исправляют его. Пользователю
   недоступен: не отдаётся в API и не показывается в UI. Правится через CLI или
   напрямую в базе.
2. **Общий промпт пользователя** — один на все его проекты, чтобы не дублировать
   одинаковые указания в каждом проекте.
3. **Промпт проекта** — специфика конкретного канала.
4. **Контент-план** — текущий слот плюс остальной актуальный план как контекст
   связности.

Правило, которое нельзя потерять при реализации: **соседние слоты передаются
только для связности, заимствовать из них факты запрещено**. Проверка
конкретики (слой 3) сверяет пост исключительно с текущим слотом.

## 8. Конвейер агента

```
слот плана (publish_at, рубрика, тема)
  → сборка контекста (три уровня промптов + план + последние посты)
  → шортлист изображений из пула проекта
  → генерация: текст поста + выбранный asset_id + обоснование выбора
  → слой 1  формальные проверки        (код, без LLM)
  → слой 2  следование инструкциям     (LLM-судья по чеклисту project_rules)
  → слой 3  конкретика сверх слота     (извлечение сущностей + сверка со слотом)
  → слой 4  соответствие картинки      (vision)
  → repair loop, не более 2 итераций, на вход подаётся список нарушений
  → статус needs_review либо автопубликация по настройке проекта
```

Генерация запускается заранее: `generate_at = publish_at − generation_lead_minutes`.

Слой 3 в деталях: регуляркой извлекаются числа, проценты, даты, время, суммы,
URL, упоминания, телефоны, email; LLM извлекает имена, названия компаний,
цитаты и ссылки на источники. Каждая сущность сверяется с текстом слота и
настройками проекта с нормализацией (`12 марта` ≈ `12.03`). Не нашли опоры —
нарушение.

Следствие для UI, о котором надо предупредить пользователя: **вся конкретика
должна быть в теме слота**, иначе её не будет в посте.

## 9. Мультипользовательская модель

- Проект принадлежит одному пользователю. Совместного доступа нет.
- Все запросы фильтруются по текущему пользователю. Чужой `project_id`
  отвечает 404, а не 403 — существование чужих проектов не раскрывается.
- Ролей, участников и приглашений нет.
- Конфликта одновременного редактирования не существует по постановке.

### Вход через Telegram-бота

Механика переносится из FakeTG:
`~/Desktop/FakeTG/mockups/telegram-web/storychat-telegram-auth.mjs`,
проверочный сценарий — `~/Desktop/FakeTG/web/check-telegram-auth.mjs`.
Читать перед реализацией, поведение воспроизводится один в один.

1. Браузер просит вход. Сервер выпускает пару токенов: `telegram_token`
   (уходит в диплинк) и `browser_token` (остаётся у браузера), и отдаёт ссылку
   `https://t.me/<bot_username>?start=login_<telegram_token>`.
2. Пользователь открывает бота, тот получает `/start login_<token>` и отвечает
   сообщением с инлайн-кнопками «Это я» / «Это не я».
3. Нажатие приходит как `callback_query` с `login_yes_<token>` либо
   `login_no_<token>`. Подтвердить может только тот же `telegram_user_id`,
   который прислал `/start`; чужое нажатие отклоняется.
4. Браузер опрашивает статус по `browser_token` раз в полторы секунды. На
   `approved` сервер ставит сессионную httpOnly cookie и гасит запрос.
5. Пользователь заводится при первом подтверждённом входе. Отдельной
   регистрации нет: `telegram_user_id` и есть личность.

Параметры, которые надо сохранить: TTL запроса на вход 10 минут, TTL сессии
365 дней, cookie `HttpOnly; SameSite=Strict; Secure` на https, проверка Origin
на POST, лимит 10 неудач с одного IP за 5 минут с ответом `429` и
`Retry-After: 300`, потолок на число одновременных запросов на вход.

Отличие от FakeTG: там запросы и сессии лежат в памяти процесса. Здесь есть
Postgres, поэтому `login_requests` и `user_sessions` — таблицы, иначе перезапуск
контейнера разлогинивает всех.

**Эксплуатационное ограничение.** `getUpdates` для одного токена допускает
ровно один опрашивающий процесс. Бот авторизации — отдельный токен и отдельный
цикл опроса внутри приложения; с доставкой в каналы (`adapters/telegram/bot_api.py`,
токены каналов в шифрованных секретах) он не пересекается. Вебхук на этом
токене одновременно с опросом не живёт. Без `AUTH_BOT_TOKEN` приложение
не поднимается — войти было бы нечем.

**Требование к реализации.** Проверка владения обязана быть встроена в общую
зависимость FastAPI, которая резолвит `project_id` до входа в обработчик.
Ручные проверки в каждом эндпоинте недопустимы: сейчас их около сорока, и
пропуск одной означает выдачу чужих данных.

## 10. Единая точка вызова модели

Расход по пользователям сейчас не пишем, ключ общий на сервер. Но подключение
учёта и биллинга позже должно быть дешёвым, поэтому:

- все обращения к модели идут через **один шлюз**, а не напрямую из адаптеров;
- каждый вызов несёт контекст: `user_id`, `project_id`, `purpose`
  (`generate`, `judge`, `claims`, `vision`, `caption`, `embedding`,
  `derive_rules`), провайдер, модель;
- шлюз вызывает хук завершения вызова, который сейчас ничего не делает.

Осознанный компромисс: пока хук пуст, исторических данных о расходе не
накапливается, и восстановить их задним числом будет неоткуда.

## 11. Фронтенд

Ведётся **параллельно другим инстансом**. Поэтому контракты API фиксируются
до начала работ — см. [api-contract.md](api-contract.md).

- Стек: React + Vite + shadcn/ui + Tailwind, TypeScript.
- Тёмная и светлая темы через класс `dark` на корневом элементе, родные токены
  shadcn, выбор в `localStorage`.
- Источник правды по внешнему виду и поведению: `ui-mockup/1-react-shadcn.html`.
  Там реализованы три вида контент-плана (список, неделя, месяц), добавление
  поста в каждом виде, сжатие колонок выходных, раскрытие плотного дня и
  предпросмотр поста по наведению с разным содержимым для каждого статуса.
- Сборка кладётся в `src/postify/web/static/`, результат сборки коммитится.
  Это сохраняет текущий способ обновления прода: `git merge` и hot reload без
  пересборки Docker.
- Backend отдаёт SPA и API из одного процесса, как сейчас.

## 12. Риски

| № | Риск | Смягчение |
|---|---|---|
| Р1 | Судья на той же модели, что и генератор, даёт коррелированные ошибки | Жёсткий чеклист, слои 1 и 3 не доверяют LLM |
| Р2 | На пост приходится 5–7 вызовов вместо одного. Латентность и стоимость **не измерены** | Запас времени на генерацию 24 часа снимает требование к скорости |
| Р3 | Пул изображений выгорает при частой публикации | Политика повторов, явная ошибка «нет доступных изображений» вместо тихого повтора |
| Р4 | Слой 3 заваливает посты без фактов | Правила зависят от рубрики |
| Р5 | Repair loop жжёт бюджет на безнадёжных случаях | Жёсткий лимит в 2 итерации |
| Р6 | Агент заимствует конкретику из соседнего слота плана | Сверка только с текущим слотом, явный запрет в промпте |
| Р7 | Пропущенная проверка владения выдаёт чужие данные | Проверка в общей зависимости, а не в обработчиках |
| Р8 | Смена образа БД на pgvector на работающем проде | Бэкап тома до деплоя, проверка на копии |
| Р9 | Вход открыт любому, кто нашёл бота: подтвердил в Telegram — получил аккаунт и проекты | Необязательный список разрешённых `telegram_user_id` в настройке; пустой список означает открытый вход |
| Р10 | Второй цикл `getUpdates` на том же токене или вебхук ломают вход молча | Отдельный токен под авторизацию, запуск цикла в одном экземпляре, ошибка Telegram пишется в журнал операций |

## 13. Предлагаемая декомпозиция

Цель — максимум параллельных треков. Конфликты возникают только на общих
файлах, поэтому их надо развести заранее.

### Подготовительный шаг, выполняется один и первым

**T0. Снос старого контура.** Затрагивает `models.py`, `bootstrap.py`,
`cli.py`, `web/routes/api.py`, `pyproject.toml` — то есть все файлы, за которые
потом будут конкурировать остальные треки. Пока он не завершён, параллелить
опасно.

В этом же шаге: разрезать `web/routes/api.py` на роутеры по доменам
(`auth.py`, `projects.py`, `plan.py`, `posts.py`, `media.py`, `rules.py`),
иначе каждый трек будет править один и тот же файл.

Там же — зафиксировать линейную цепочку ревизий Alembic и заранее раздать
каждому треку его `revision` и `down_revision`, чтобы не было гонки миграций.

### После T0 — параллельно

| Трек | Содержание | Зависит от |
|---|---|---|
| T1 | Вход через Telegram-бота: цикл опроса, `login_requests`, сессии, пользователи, зависимость владения. Снос `POSTIFY_ACCESS_PASSWORD` | T0 |
| T2 | Контент-план: слоты, рубрики, API, вычисление `generate_at`, постановка задач планировщику | T0 |

## 14. Решения, принятые при реализации T0

Фиксируются здесь, потому что затрагивают все параллельные треки.

**Цепочка миграций сброшена.** Все девятнадцать старых ревизий удалены, база
начинается с `20260911_01_baseline` — она создаёт только переживший контур.
Прод накатывается с нуля (`docker compose down -v`), это допускает Р10. Номера
ревизий: `02` занял вход через Telegram-бота, `03` и далее свободны, каждый
трек берёт следующий свободный номер и ставит `down_revision` на предыдущий.
В baseline включено `CREATE EXTENSION IF NOT EXISTS vector`, чтобы образ БД и
права проверились один раз, а не в середине работ над пулом изображений.

**Таблицы переименованы под предметную область.** `content_packages` стали
`posts`, `content_package_status_history` — `post_status_history`. В доставках,
задачах расписания и заявках на слот `package_id` и `route_id` заменены одним
`post_id`. Статусы поста: `generating`, `needs_review`, `approved`,
`rejected`, `failed`, `published` — они же статусы слота из контракта, кроме
`no_topic`, `planned` и `skipped`, которые живут только на слоте.

**Журнал операций стал универсальным.** Колонки `codex_model`,
`codex_reasoning_effort`, `materials_taken`, `packages_created` заменены одним
`result jsonb` — так требует поле `result` в контракте поллинга. Видов операций
шесть: `generate_post`, `regenerate_post`, `publish_once`, `retry_delivery`,
`derive_rules`, `caption_media`. `failure_code` обязан быть
`<operation>_failed`, это проверяет CHECK.

**`ExecutionContext` удалён.** Вместо девяти комбинаций режима, актора и цели
операция принимает `mode` и `actor` явными строками. Ручные цели
(`target_attempt_id` и прочие) исчезли вместе со старым контуром.

**Адаптер Codex разобран на транспорт.** `CodexContentAnalyzer` заменён на
`adapters/ai/codex_cli.py`: `complete(prompt, output_schema=None)` запускает
`codex exec` в одноразовом каталоге с тем же набором `--disable` и отдаёт текст.
Ни промптов, ни разбора ответа в нём нет — это задача шлюза вызовов модели
(T4). Gemini-адаптер старого контракта удалён: его контракт вживую не
подтверждён, HTTP-провайдера собирает T4.

**Префикс API — `/api`,** а не `/api/v1`, как требует контракт. Формат ошибки:
`{"error": {"code", "message", "request_id"}}`.

**Общий пароль `POSTIFY_ACCESS_PASSWORD` и создание проекта из переменных
окружения удалены.** Проекты создаёт пользователь, вход — только через бота.

**Словарь актора приведён к контракту:** `operation_runs.actor` принимает
`scheduler` и `user`; значения `ui` больше нет.

**Швы, оставленные следующим трекам.** Колонка `content_projects.topic`
сохранена и при создании заполняется названием проекта — трек промптов (T5)
переименует её в `project_prompt`, отдельной колонки заводить не нужно. Поля
`publication_mode`, `generation_lead_minutes`, `media_reuse_days` из контракта
добавляют треки публикации, контент-плана и пула изображений; расширять надо
`EDITABLE_FIELDS` в `application/projects/manage_project.py` и
`ProjectConfiguration`. Проверка `rubric_in_use` собрана, но всегда разрешает
удаление: трек контент-плана добавляет в репозиторий проектов
`count_rubric_slots(project_id, rubric_id)`, и проверка включится сама —
тест на это уже написан.

## 15. Состояние после T0 и T1

Ветка `ui-mockup-content-plan`, коммит с переработкой — `a7787a8`.
222 юнит- и 84 интеграционных теста зелёные, `alembic check` без расхождений.

**Готово и переиспользуется.** Проект с рубриками и каналом, посты с
редакторскими решениями и планом публикации, доставка в Telegram с журналом
попыток, планировщик с восстановлением задач после перезапуска, журнал
операций с поллингом, вход через бота с изоляцией по владельцу, транспорт
Codex, шифрование секретов канала.

**Ревизии Alembic.** Заняты `20260911_01` (baseline) и `20260911_02`
(пользователи и владение). Следующий трек берёт `20260911_03` и далее,
`down_revision` ставит на предыдущую занятую.

**Проверка владения.** Каждый роутер с `project_id` объявляет
`Depends(owned_project)` на уровне роутера, поэтому новый эндпоинт физически
не может появиться без проверки. Есть тест, который обходит все маршруты и
падает, если у какого-то зависимость отсутствует — при добавлении роутеров его
трогать не нужно, он найдёт пропуск сам.

**Единственные маршруты без `project_id`** — `GET` и `POST /api/projects`.
Там владелец берётся из сессии и передаётся в репозиторий явным `owner_id`.

**Чего в фасаде пока нет.** `SUPPORTED_OPERATIONS` содержит только
`publish_once` и `retry_delivery`; `generate_post`, `regenerate_post`,
`derive_rules` и `caption_media` объявлены в перечислении и разрешены базой,
но обработчика не имеют — его приносит трек генерации вместе со шлюзом
вызовов модели.

**Поля контракта на заглушках.** `project_prompt`, `publication_mode`,
`generation_lead_minutes`, `media_reuse_days` отдаются константами и не
принимаются в `PUT`; `media: {total, available}` нули; `post.slot_id` и
`post.validation` всегда `null`; `project_summary.counts` считает статусы
постов, а не слотов. Каждое из этих мест закрывает свой трек.

**Запуск тестов.** Юнит: `.venv/bin/python -m pytest tests/unit -q`.
Интеграционные требуют PostgreSQL с расширением vector:

```
docker run -d --name postify-dev-db -e POSTGRES_USER=postify \
  -e POSTGRES_PASSWORD=dev -e POSTGRES_DB=postify -p 55432:5432 \
  pgvector/pgvector:pg17
TEST_DATABASE_URL=postgresql+psycopg://postify:dev@127.0.0.1:55432/postify \
  .venv/bin/python -m pytest tests/integration -q
```

**Что решено по открытым вопросам T1.** Без `AUTH_BOT_TOKEN` процесс не
поднимается — проверка стоит в `container_start.py`, то есть на границе
развёртывания; `create_app` при этом собирается, иначе тесты требовали бы
живого бота. Запрет по списку разрешённых `telegram_user_id` проверяется уже
после подтверждения в боте: пользователь видит «Вход подтверждён» в Telegram,
а браузер получает `403 login_not_allowed`. Это осознанный компромисс, чтобы
не заводить пятый статус запроса на вход.

**Деплой.** Образ БД сменился, поэтому накат на прод — только через
`docker compose down -v` и подъём с нуля: данные стираются по Р10.
