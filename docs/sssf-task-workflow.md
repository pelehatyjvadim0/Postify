# Как ставить задачи на реализацию

## Что писать в задаче

Пиши задачу обычным сообщением. Достаточно четырёх частей:

1. **Результат** — что должно появиться или измениться.
2. **Контекст** — где это находится и зачем нужно.
3. **Готовность** — по каким наблюдаемым признакам принять результат.
4. **Ограничения** — что нельзя менять, какие совместимости и форматы сохранить.

Пример:

> Реализуй создание фермы через API. Пользователь передаёт название, нишу и часовой пояс. Готово, когда ферма сохраняется, возвращается через API, повторное имя получает понятную ошибку, а тесты проходят. Текущий контентный конвейер и миграции прошлых версий не ломай.

Не нужно расписывать план реализации, назначать агентов, перечислять этапы проверки или просить сделать коммиты — это выбирает рабочий цикл.

## Когда добавлять уточнения

- Если нужен конкретный workflow, назови ADW явно: `выполни через adw_simple_sdlc`.
- Если нужен конкретный набор моделей, назови roster. Без указания используется default roster.
- Если задача продолжает прежний запуск, передай его `adw_id`.
- Для исследования без изменений прямо напиши: `только изучи, ничего не меняй`.

## Твой рабочий процесс

1. Ты отправляешь задачу с результатом, критериями готовности и ограничениями.
2. Оркестратор проверяет упомянутые пути, выбирает подходящий ADW и запускает задачу.
3. После запуска ты получаешь фактически переданный промпт, выбранные ADW и roster, а также `adw_id`.
4. По `adw_id` можно в любой момент спросить статус, посмотреть текущую фазу или остановить запуск.
5. После завершения ты получаешь статусы фаз, результаты проверок, список изменений и коммиты.
6. Ты проверяешь результат и отдельно разрешаешь отправку в GitHub. Без твоего подтверждения push не выполняется.

## Текущее ограничение

SSSF уже установлен как основной цикл, но установленный runtime пока настроен на Pi. Реализационные запуски начнут работать после следующего шага — подключения Codex-адаптера. До этого конфигурация моделей и roster остаётся без изменений.
